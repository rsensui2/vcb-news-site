日本語訳全文

Markdown は AI エージェントが我々と意思疎通するためのデフォルトファイル形式になった。シンプルで、ポータブルで、リッチテキストもそこそこ表現でき、編集も楽だ。Claude は markdown 内に ASCII で図を描くのもかなり上手くなった。

しかしエージェントが強くなるにつれ、私は markdown が制約になっていると感じ始めた。100行を超える markdown は読む気がしない。もっとリッチな視覚化、色、図表が欲しいし、それを簡単に共有したい。

そして私は最近、こうしたファイルを自分で編集することはほとんどなく、仕様書・参照資料・ブレストの出力として使っている。編集するときも結局 Claude にプロンプトで指示するので、markdown の最大の利点（人間が編集できる）も消えてしまう。

そこで私は出力フォーマットとして markdown より HTML を好むようになった。Claude Code チームの他のメンバーの間でも増えている。その理由を書く。

(サンプル: https://thariqs.github.io/html-effectiveness)

なぜ HTML か？

情報密度 — HTML は markdown よりもはるかにリッチな情報を表現できる。テーブル、CSS によるデザインデータ、SVG イラスト、コードスニペット、JS によるインタラクション、ワークフロー、空間データ、画像。Claude が読める情報のうち、HTML で効率的に表現できないものはほぼない。

視覚的な分かりやすさ・読みやすさ — 実際 100 行超の markdown は読まない。HTML は構造を視覚的に整理でき、タブ・図・リンクで巡回でき、モバイル対応もできる。

共有のしやすさ — Markdown はブラウザがそのまま綺麗にレンダリングしないので共有しづらい。HTML は S3 にアップすればリンク 1 本で共有できる。スペックや報告書を実際に読んでもらえる確率が大幅に上がる。

双方向インタラクション — HTML ならスライダーやノブで調整させたり、結果を「コピーして Claude にペースト」させたりもできる。

データ取り込み — Claude AI や Claude Design ではなく Claude Code で HTML を作る理由は、Claude Code がファイルシステム、MCP（Slack/Linear など）、ブラウザ（Claude in Chrome）、git history など膨大なコンテキストを取り込めるから。

楽しい — Claude と HTML を作るのは単純に楽しく、自分が制作に深く関わっている実感が出る。

始め方

「これを /html スキルにするんでしょ？」と思われそうだが、しないでほしい。素朴に「HTML ファイルを作って」「HTML アーティファクトを作って」と頼むだけでいい。コツは、そのアーティファクトに何をさせたいか・どう使いたいかを自分で分かっていること。

ユースケース

  • 仕様・計画・探索 — Markdown のプラン 1 枚ではなく HTML ファイルの「網」を作る。ブレスト、モックアップ、コードスニペット、実装プランを順に積み、満足したら新セッションでまとめて実装させる。検証エージェントにも同じファイル群を渡せる。
  • コードレビュー・コード理解 — diff、注釈、フローチャート、モジュール図を埋め込める。GitHub のデフォルト diff より分かりやすい。すべての PR に「HTML コード説明書」を添付している。
  • デザイン・プロトタイプ — Claude Design は HTML ベース。React や Swift が最終形でも、まず HTML でデザインさせ、その後言語に翻訳させる。アニメーションのチューニング用にスライダーを差し込ませることもある。
  • レポート・リサーチ・学習 — Slack、コードベース、git history、Web を横断して合成し、長文 HTML、インタラクティブな解説、スライドにする。SVG で図解させる。
  • 使い捨て編集 UI — Linear チケット 30 件をドラッグで Now/Next/Later/Cut に振り分けて「copy as markdown」させる、フィーチャーフラグの設定エディタ、左右並列のプロンプトチューナーなど、その場限りの専用 UI を HTML 1 枚で作らせる。「export」ボタンで結果を Claude にペーストし直せる形にするのがコツ。
  • その他、データセット選別、注釈付け、色やイージング曲線・cron 式・正規表現みたいな「言葉で書きにくい値」のピッカー。

よくある質問

  • トークン効率悪い？ Markdown より食うのは事実。だが表現力と「実際に読まれる確率」が上がるので結果的に得。Opus 4.7 の 1MM コンテキストなら気にならない。
  • Markdown はいつ使う？ ほぼ使わなくなった。
  • どう見る？ ブラウザでローカルに開く、または S3 にアップ。
  • 生成が遅い？ 2-4倍。だが価値はある。
  • バージョン管理は？ 最大の弱点。HTML diff はノイジーで読みづらい。
  • デザインがダサくならない？ Frontend design plugin を使う。自社テイストに合わせるなら、コードベースから design system HTML を 1 枚作って参照させる。

Loop に入っている感

結局のところ、HTML を使う本当の理由は「Claude のループに自分が入っている感」だ。プランを深く読まなくなった結果 Claude の判断に委ねるしかなくなる、と恐れていた。HTML にしたらむしろ今までで一番ループに入っている。皆さんもそうあれ。

まとめ

Claude Code チームの Thariq による「HTML is the new markdown」論。AI エージェント時代の出力フォーマットとして、Markdown よりも HTML の方が情報密度・視覚性・共有性・双方向性すべてで優位、と主張。Opus 4.7 の 1MM context window が前提。
