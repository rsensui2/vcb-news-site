概要

「ループ（loop）」が話題だが、その下で動く ハーネス（harness＝1体のエージェントが動く環境そのもの） を語る人がほとんどいない、という問題提起の X Article。著者は Addy Osmani の「ループ工学はハーネスの一階上にある」という整理を引きつつ、9割の開発者が Claude Code をデフォルト構成（ルール・サブエージェント・hook・メモリなし）のまま使うから loop が "slop（ゴミ）" を量産する、と指摘する。ハーネスとは突き詰めれば4要素——①思考するモデル、②使えるツール、③ツールの権限、④起動時に読むコンテキスト——だけで、subagent・hook・memory はこの4つのどれかを形作る手段にすぎない、と定義する。

まとめ

  • 3 層を混同しない: harness（1体の静的な実行環境）/ loop（タイマーで回り helper を生み自分に餌を与える）/ self-improving system（loop＋蓄積するメモリ）。役割を混ぜるのが「設定がぐちゃぐちゃ」の根本原因。
  • CLAUDE.md は "立っている事実" だけ・短く（〜500トークン目安）。手順は skill へ、フォルダ固有のルールは rules/ へ。手順書化して肥大させるのが最頻出のミス。
  • settings.json で権限を一度だけ設計: 「失敗したら元に戻すのが安いか高いか」で自動承認/拒否を判断（force-push・ファイル削除・secret 操作は常に拒否/確認）。
  • subagent は "汚れ仕事" を隔離する別コンテキスト。最も価値が高いのは「メインエージェントの成果をチェックするレビュアー」。自分の出力を自分で採点すると甘くなる（writer-vs-checker 分離）。
  • skill＝再利用する手順、hook＝モデルが幻覚できない決定論的ルール。hook は exit code 2 で危険コマンド（rm -rf, .env 読み取り, main への push）をブロックでき、「提案」の CLAUDE.md と違い「強制」。鋭い hook を1〜2個、20個並べない。
  • memory が "設定済みハーネス" を "改善するシステム" に変える: 走り終わりに state file へ学び・検証済み事実・次の一手を書き、開始時に読む。一般化できた学びは skill に昇格させる。
  • 順序が教訓: まずクリーンな環境で1回の手動実行を安定させる → コンテキストと権限 → レビュアー subagent → memory → *その後で初めて* loop を被せる。悪いハーネスに loop を被せると速くゴミを垂れ流すだけ。

日本語訳全文

誰もが loop（ループ）の話をしている。だが、その loop が「何の上で動いているのか」を語る人はほとんどいない。10人中9人の開発者は、Claude Code をデフォルトのハーネスのまま動かしている——ルールもなし、subagent もなし、hook もなし、memory もなし。

そして、なぜ自分の loop が slop（ゴミ）を吐き出すのかと首をかしげる。真実はシンプルだ。loop の良し悪しは、その下にあるハーネスの良し悪しで決まる。これは、1体のエージェントから「自分自身を改善するシステム」へと至る14ステップのロードマップである。

最新の AI alpha（先取り情報）が欲しければ、私の Substack をフォローしてほしい: movez.substack.com

loop 工学——エージェントをスケジュールに沿ってプロンプトで起動するシステムを作ること——は今月、大いに注目を集めた。だが loop について長文の記事を書いた Addy Osmani は、その下にあるものを慎重に指し示していた。

「loop 工学はハーネスの一階上に位置する。ハーネスとは、1体のエージェントがその内側で動く環境そのものだ。loop はハーネスではあるが、タイマーで回り、helper を生み出し、自分自身に餌を与える。」

ハーネス工学とは、その環境を設計することだ——モデル、ツール、権限、コンテキスト、memory。

それは華やかさのない層であり——そして、その上にあるすべてが機能するかどうかを決める層でもある。悪いハーネスの上に乗った優れた loop は、ゴミを大量生産する近道にすぎない。

14ステップ。3つの階層（tier）。すべてが立つための土台。

Part 1 · ハーネスとは何か

01. ハーネスとは、1体のエージェントがその内側で動く環境のことだ。

専門用語をはぎ取れば、ハーネスとは4つのものに集約される。思考をするモデル、それが到達できるツール、それらのツールにかかる権限、そして実行のたびに最初に読むコンテキスト。

それがハーネスの全表面だ。それ以外のすべて——subagent、hook、memory——は、この4つのうちのどれかを形作るための手段である。

ハーネスが人々の思う以上に重要な理由はこうだ。エージェントとは、ツールを選び、それを実行し、結果を見て、次の一手を決める、という while True ループである。

ハーネスは、どんなツールが存在するか、エージェントが何をしてよいか、そして開始時に何を知っているか、を定義する。同じモデルでも、ハーネスが違えば、まったく別のエージェントになる。

02. ハーネス全体は1つのフォルダの中にある。.claude/

エージェントを形作るすべてが、プロジェクトルートにある単一のディレクトリに収まっている。このレイアウトを覚えれば、誰のハーネスでも一目で読み取れるようになる。

きれいなハーネスとぐちゃぐちゃなハーネスを分ける1つのルール: なぜ各ファイルが存在するのかを説明できる程度に、小さく保つこと。あるルール・hook・subagent が何のためにあるか言えないなら、削除すること。

03. ハーネス vs loop vs システム。3つの階（floor）、混ぜるな。

「自分のエージェント構成がぐちゃぐちゃだ」という問題の大半は、この3つの階を混同することから生じる。きちんと区別しよう。

ハーネスとは、1体のエージェントが住む実行環境（runtime）だ。静的な設定: モデル、ツール、権限、コンテキスト。この記事のテーマがこれ。

loop はエージェントをタイマーで起動し、helper を生み、自分自身に餌を与える。これはハーネスの上で動く。

自己改善システム（self-improving system）は、loop に「複利的に積み上がる memory」を加えたものだ——どの実行も、次の実行をより鋭くする。

実践的に言えばこうなる: 立っている事実はコンテキストに、強制はhookに、手順は skill に、隔離は subagent に置く。

これらを取り違えること——強制を CLAUDE.md に書く、手順がコンテキストを肥大させる——こそが、一貫性がなく高コストなエージェントの根本原因だ。

04. デフォルトのハーネス。箱から出した状態で手に入るもの。

Claude Code をインストールし、フォルダを開けば、もうハーネスは手に入っている——ただし空っぽのものだ。デフォルトでは、有能なモデル、組み込みツール（read, write, bash, search）、そしてあらゆる危険操作に対する承認プロンプトが付いてくる。プロジェクトのコンテキストはなし、カスタム subagent はなし、memory はなし。

一回限りのタスクなら、デフォルトで十分だ。だが2回以上やる作業なら、デフォルトはエージェントに毎セッション、プロジェクトをゼロから再導出させ、安全な操作にいちいち許可を求めさせ、ターミナルを閉じればすべてを忘れさせる。

続く10ステップは、そのギャップを埋めるためのものだ。

05. CLAUDE.md: 立っている事実を、短く保つ。

CLAUDE.md は毎セッションの開始時に読まれる。それはエージェントがあなたのプロジェクトについて常時持っておく知識だ——規約、アーキテクチャ、「あの事故があったから我々はこのやり方をしない」といったこと。

最もよくある間違い: これを、毎セッションを肥大させる巨大な手順書へと成長させてしまうこと。

これを毎日運用している実践者からのルール: メインの memory ファイルは〜500トークン未満に保つこと。立っている事実はここに置く。

複数ステップの手順は skill へ（ステップ8）。パス固有の振る舞いは、適用される場所にスコープされた rules/ ファイルへ。CLAUDE.md のあるセクションが事実ではなく手順になってしまっているなら、それは別の場所に属すべきものだ。

自分の CLAUDE.md を声に出して読んでみよう。どの行も、エージェントが毎セッションで必要とする事実であるべきだ（「我々は npm ではなく pnpm を使う」）。ある行が手順なら（「機能を追加するには、まず…」）、それは skill へ移す。

それが1つのフォルダのためのルールなら、rules/ へ移す。

06. settings.json: 権限とモデルを、一度だけ設定する。

デフォルトのハーネスは、危険なアクションのたびに確認を求める。それはあなたが見ているときには正しく、見ていないときには間違っている。settings.json は、安全なものを事前承認し、危険なものを拒否し、どのモデルを動かすかを選ぶ場所だ。

何を自動承認すべきかの判定基準: これが失敗したとき、元に戻すのはどれくらい大変か。元に戻すのが安い → 自動承認。

元に戻すのが高い（force-push、ファイル削除、secret に触る）→ 常に拒否か確認。中間にあるものは、ログを取るなら自動承認してかまわない。

07. Subagent: 汚れ仕事のための隔離されたコンテキスト。

subagent とは、メインのセッションから起動される独立した Claude セッションだ——独自のコンテキストウィンドウ、独自のツールリストを持つ。狙いは、並列化そのもののためではない。メインのコンテキストからノイズを締め出すことにある。

40ファイルを読む調査タスク、新鮮な視点を要するレビュー工程、大量のログを吐き出す eval 実行——こうしたものは、メインスレッドを汚さないように subagent に入れるべきだ。

どんなハーネスでも最も価値が高い subagent は、メインエージェントがやった仕事をチェックするものだ。モデルが自分自身の出力をレビューすると、自分に甘くなりすぎる。

新鮮なコンテキストウィンドウを持つ別のレビュアーは、書き手が自分を言いくるめてしまった部分を捉える。これが writer-vs-checker（書き手と検査役）の分離であり、ハーネスの上にあるあらゆる loop を信頼できるものにする。

08. Skills: エージェントが再利用する手順。

Skill とは、エージェントが実行する SKILL.md ファイルだ——/skill-name で呼び出したときか、タスクがその説明にマッチしたときに自動で実行される。

subagent と違い、これは同じコンテキストウィンドウ内で動く。それは単に、セッションの一部となる再利用可能な指示書にすぎない。

作るべきタイミングのサイン: 新しい会話のたびに同じ指示をペーストしている自分に気づくこと。それは skill になりたがっている。PR チェックリスト、eval 手順、リリースプロセス——一度書けば、永遠に呼び出せる。

そして skill は再利用の単位であるがゆえに、ハーネスを時とともに改善させるものでもある。手順が新しい形で失敗するたびに、その教訓を skill に追加すれば、次の実行はそれを引き継ぐ。

09. Hooks: モデルが幻覚できない決定論的なルール。

ここまでのすべては、モデルがあなたの指示を理解していることに依存していた。hook はそうではない。

hook とは、エージェントのライフサイクルの決まった地点で発火するシェルコマンドだ——ツールが実行される前、ファイルが変更された後、セッションが終わるとき——そしてその exit code はアクションをブロックできる。hook は強制であり、CLAUDE.md は提案である。

ほぼすべてのハーネスでその場所に値する hook が2つある:

危険なコマンドを決定論的にブロックする PreToolUse ゲート——rm -rf、.env の読み取り、main への push。exit code 2 が、呼び出しが起こる前にそれを止める。モデルはそれを言葉で言い抜けられない。

すべての編集の後にあなたの linter または formatter を走らせる PostToolUse フォーマッタ。ハーネスが自動でフォーマットしてくれるので、エージェントが未整形のコードを世に出すことは決してない。

必ず起こるべきこと・絶対に起きてはならないことには hook を使う——安全性、フォーマット、監査ログ。

判断を要する事柄には使わないこと。それはモデルの役目だ。良いハーネスは鋭い hook を1〜2個持つ。20個ではない。

Part 3 · 複利を効かせる

10. loop を加える。今やハーネスはタイマーで動く。

設定済みのハーネスでも、まだあなたがタイプするのを待っている。loop はそれを自律的に動かす。最もシンプルな形は Claude Code の /loop だ——一定のリズムで繰り返されるプロンプト。

これを /goal と組み合わせれば、loop は目的条件が真になるまで回り続ける。しかもその判定は、エージェント自身が採点するのではなく、独立した採点者がチェックする。

たった今、何が起きたかに注目してほしい。loop は知性を追加していない。loop はハーネスの中のすべてを再利用しただけだ——ルール、レビュアー subagent、安全 hook。良いハーネスは loop を些細なものにする。それこそが、土台を先に作ることの全目的だ。

11. 動的ワークフローを加える。ハーネスが自分自身のオーケストレーションを書く。

単一の loop には複雑すぎるタスク——大規模に並列、高度に構造化、敵対的（adversarial）——には、Claude がその場で自分自身の JavaScript ハーネスを書ける。

それが動的ワークフロー（dynamic workflow）だ: 生成する agent()、扇状に広げる parallel()、ストリームする pipeline()。それは、ハーネスが定義する subagent を、fan-out-and-synthesize（扇状展開して統合）や adversarial verification（敵対的検証）といったパターンへと構成する。

ハーネス工学との結びつき: 動的ワークフローの良し悪しは、それが呼び出せる subagent と skill の良し悪しで決まる。

あなたのハーネスに鋭いレビュアー subagent と、よく書かれた eval skill があれば、ワークフローはオーケストレーションすべき良い部品を持つことになる。ハーネスが空っぽなら、ワークフローには使えるものが何もない。

ワークフローは指揮者であり、あなたのハーネスはオーケストラだ。

12. memory を加える。エージェントが忘れることを、ハーネスは覚えている。

これが、設定済みのハーネスを「本当に改善するシステム」へと変えるステップだ。エージェントは実行と実行の間にすべてを忘れる。だがハーネスは忘れる必要がない。

state file——agent-memory/ の中の markdown ファイル、あるいは Linear ボード——が、何が試されたか、何が効いたか、何が失敗したか、どのルールが生き残ったかを記録する。

memory を複利的にするパターンを、最強のエージェントたちの使い方から引いて示す:

去る前に書く。どの実行も、state file の更新で終わる——学んだ教訓、検証済みの事実、次にやること。

開始時に読む。どの実行も、state file と関連 skill を読むことから始まる。そうすれば、再スタートではなく再開ができる。

skill へ蒸留する。教訓が一般化できたら（「Windows ランナーは PowerShell ではなく bash が要る」）、それは state file から skill へと昇格し、そこで未来のすべてのプロジェクトに適用される。

13. loop を閉じる。出力 → 教訓 → skill → より良い出力。

ここで、3つの階が組み合わさって、自分自身を改善する何かへとロックされる。どの実行も出力を生む。レビュアー subagent（ステップ7）がそれをチェックする。

その結果——何が通り、何が失敗し、何を学んだか——が memory（ステップ12）に書き込まれる。一般的な教訓は skill（ステップ8）へと蒸留される。次の実行は、より鋭い skill とより豊かな memory を引き継ぐ。

それが自己改善ループの全体であり、それがすべてハーネスの部品から組み立てられていることに注目してほしい:

subagent が仕事を採点する——客観的なチェック、新鮮なコンテキスト。

memory が判定を記録する——実行と実行の間を生き延びる。

skill がそれをもう一度走らせる——今や、前回の実行が学んだすべてを携えて。

loop がそれをもう一度走らせる——今や、前回の実行が学んだすべてを携えて。

モデルは一切変わっていない。その周りのハーネスがより鋭くなった。それが「自己改善」が正直に意味するところだ——学習するモデルではなく、蓄積するハーネス。

14. ハーネスを出荷する。パッケージ化し、共有し、再利用する。

1つのプロジェクトで機能するハーネスは資産だ。

skill、subagent、rules をプラグインにまとめれば、チーム全体がワンステップで同じ構成をインストールできる——同じ規約、同じ安全 hook、同じレビュアー。

ハーネスはあなた個人の構成であることをやめ、共有インフラになる。

構築すべき順序を、最後にもう一度——順序こそが教訓だから: まずクリーンなハーネスの上で、1回の手動実行を確実にする。

コンテキストと権限を加える。レビュアー subagent を加える。memory を加える。そして——その後で初めて——それを loop で包む。良いハーネスの上の loop は複利を生む。悪いハーネスの上の loop は、ただより速く血を流すだけだ。

§ あらゆる loop を悪化させるハーネスの間違い

デフォルトのまま動かす。コンテキストなし、ルールなし、memory なし——エージェントは毎セッション、あなたのプロジェクトを再導出する。

肥大した CLAUDE.md。手順が立っているコンテキストに詰め込まれ、毎実行を肥大させる。skill へ移すこと。

強制を hook ではなく CLAUDE.md に書く。モデルは提案を無視できる。exit 2 する hook は無視できない。

1体のエージェントが自分の仕事を書いて自分で採点する。新鮮なコンテキストウィンドウを持つレビュアー subagent を加えること。

memory がない。どの実行もゼロから再スタートする。state file こそが、明日を再開させるものだ。

悪いハーネスの周りに loop を巻く。loop はただ slop をより速く生むだけ。先に土台を作ること。

20個の hook。鋭い1〜2個が、誰も理解できない山に勝る。

スキャンせずにハーネスを出荷する。漏れた secret や広すぎる権限が、それをインストールする全員へ拡散する。

結論:

loop が栄光を得る。仕事をするのはハーネスだ。

loop 工学は心躍る部分だ——エージェントが自分自身をプロンプトで起動し、あなたが眠っている間に走る。だが loop は、タイマーで動くハーネスにすぎない。

出力が良いかゴミかを決めるすべては、一階下に住んでいる——あなたが選んだモデル、あなたが許したツール、あなたが書いたコンテキスト、あなたが加えたレビュアー、あなたが保った memory に。

その階をうまく作れば、その上のすべてが複利で積み上がる: loop はあなたの subagent を再利用し、ワークフローはあなたの skill をオーケストレーションし、memory は各実行を前回より鋭くする。

自己改善は、決してモデルの性質ではなかった。それは、あなたがその周りに築くハーネスの性質だ。

あなたがやっていない1つを選べ——おそらくレビュアー subagent、安全 hook、あるいは state file だろう——そして今日それを加えよ。ハーネスは説明できる程度に小さく保て。それから、その上に loop を乗せ、土台が仕事をするのを見届けよ。
