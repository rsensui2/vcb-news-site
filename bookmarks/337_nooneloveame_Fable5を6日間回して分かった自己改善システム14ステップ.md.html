概要

「新モデルは速い」系のホットテイクを避け、Fable 5 エージェントを6日間ノンストップで放置して観察してから書いた、という異色の長文 X Article。著者の主張は「ほとんどの人が宇宙船をスクーターのように運転している」——Fable 5 を "コンテキスト窓が大きい Sonnet 4.6" 程度に扱い、数分のチャットで閉じてしまう。Fable 5 は本来 "何日も走り続ける" ために作られたモデルで、その endurance を活かすには毎回の実行が次の実行を賢くする「自己改善する仕組み」を外側に組む必要がある、と説く。

まとめ

  • Fable 5 とは: 2026-06-09 公開、初の一般提供 Mythos クラス（Anthropic が Opus の1つ上に置いた階層）。エージェントハーネス内で数日自律稼働し、段階をまたいで計画、サブエージェントに委任、vision で自分の出力を検証。価格は 入力 $10 / 出力 $50 per M トークン（入力は90%プロンプトキャッシュ割引あり）。定額ではなく重課金。
  • self-learning と self-improving の区別: 重みを自分で更新するのが self-learning（現行モデルはやらない）。self-improving は "モデルの周りの仕組み" が蓄積すること——記憶に学びを書き、skill が鋭くなり、state file に検証済み事実が積もる。モデルは凍結、環境が毎回鋭くなる。
  • 4 層スタックを下から積む: Layer1 primitives（Fable5・subagent・worktree）→ Layer2 orchestration（goal loop・Dynamic Workflows・Routines）→ Layer3 memory（state file・Skills・知識ベース）→ Layer4 self-improvement（vision 自己チェック・eval ループ・ルール蒸留）。
  • タスクでモデルをルーティングする（全部 Fable 5 で回さない）: オーケストレータ＝Fable 5、難所の限定タスク＝Opus 4.8（安全分類器ブロック時の自動フォールバックも兼ねる）、高volume の worker＝Sonnet 4.6、grader/分類器＝Haiku 4.5。
  • 検証は必ず別 subagent（自己批評しない）: Claude Code チームが Fable 5 で直接確認——独立 verifier が self-critique に勝つ。自分の推論過程が見えると自分の結論を贔屓するため。

軽い前提知識：Fable 5 とは実際のところ何なのか

Fable 5 は 2026年6月9日に、初の一般提供 Mythos クラスのモデルとしてローンチした——Anthropic が Opus の1つ上に置いた階層だ。

エージェントハーネスの内側で何日も自律的に走り、複数の段階をまたいで計画を立て、サブエージェントに委任し、vision で自分の作業を検証するように作られている。

価格はその階層に見合っている：入力 100万トークンあたり $10、出力 100万トークンあたり $50、入力には90%のプロンプトキャッシュ割引がつく。これは定額のサブスクリプションではない。重く使えばそれ相応の請求が来る。

だから全体のゲームは、高価な実行を2回ぶん回収すること——いま1回、そして次の実行をより良くすることでもう1回——だ。

PART 1: Fable 5 が解き放つもの

ステップ1：チャットボックスではなく、何日も働くワーカーとして扱え

見出しになるのは endurance（持久力）だ。Claude Code または Claude Managed Agents の内側で走らせれば、Fable 5 は何日も働ける——フェーズをまたいで計画し、サブエージェントを生成し、進めながら自分自身を検証する。

自分でテストを書く。vision を使って出力をゴールと照合する。学んだことを再利用可能なルールへ蒸留する。

Anthropic が筆頭に挙げるユースケースが全てを物語っている：大きなプロジェクトを丸ごと預けて、戻ってきたら完成した成果物をレビューする。大規模な移行、何日もかかるビルド、サインオフ可能な状態で終わるディープリサーチ。

もしセッションが5分で終わるなら、あなたは Mythos 価格を払ってスクーターに乗っているだけだ。

ステップ2：self-improving と self-learning の違いを知れ

ここでほとんどの人が混乱するので、正確に言いたい。

self-learning とは、モデルが学んだことから自分の重みを更新することを指す。Fable 5 はこれをやらない。本番のモデルはどれもやらない。それは Anthropic 自身が慎重に構えてきた長期的な方向性であって、今日出荷されているものではない。

self-improving とは、モデルの周りのシステムが複利的に積み上がることを指す。各セッションが学びを記憶に書き込む。エッジケースが積もるにつれて Skills が鋭くなる。state file に検証済みの事実が蓄積される。eval ループがプロンプトとルーブリックを磨いていく。

モデルは凍結されたままだ。それが走る環境が、1回走るたびに鋭くなる。

この区別こそが、この記事の全てだ。self-improvement はあなたが組み上げるシステムの性質であって、モデルの機能ではない。

ステップ3：複利スタックを下から積み上げろ

4つの層で考えろ。順番に組め。なぜならレバレッジは順番に積み重なるからだ。

Layer 1 は primitives（プリミティブ）——Fable 5 そのもの、サブエージェント、worktree、生のツール。ほとんどの人が触れるのはここまでだ。

Layer 2 は orchestration（オーケストレーション）——自己修正のための goal loop と Outcomes、複数ステップのオーケストレーションのための Dynamic Workflows、ノートパソコンを閉じたままクラウドで走らせる Routines。

Layer 3 は memory（記憶）——state file、Skills、知識ベース、書き留められた学び。明日が再起動ではなく再開になるようにするためのものだ。

Layer 4 は self-improvement（自己改善）——vision 自己チェック、eval ループ、ルール蒸留。エージェントが自分の出力を採点し、それを生んだ Skill を鋭くし、そして学びを記憶へ書き戻す。

複利的になる理由はこうだ。Layer 1 からのすべての出力が Layer 4 まで上がり、採点され蒸留され、そして Layer 3 へ落ちてくる。明日の実行は、昨日鋭くなった記憶を受け継ぐ。モデルはステートレスだ。システムはそうではない。

ステップ4：タスクでルーティングしろ、すべてを Fable 5 で走らせるな

Fable 5 はトークンあたりで Opus 4.8 のおよそ5倍のコストがかかる。すべてのステップが最上位階層に値するわけではない。これを本番で回しているチームは、習慣ではなく複雑さでルーティングしている。

Fable 5 はオーケストレータの役割を担う——何日もまたいで計画し、委任し、vision で作業をチェックし、蓄積された証拠からルールを蒸留する。

Opus 4.8 は難しいが範囲が限定されたサブタスクを担う——アーキテクチャの判断、厄介なデバッグ、深いレビュー。さらに Fable 5 の安全分類器がリクエストをブロックしたときの自動フォールバックでもある。

Sonnet 4.6 は高volume のワーカータスクを処理する——lint パス、単純なリファクタ、テストの足場づくり、ドキュメント更新。ファンアウト作業の大半はここに住む。

Haiku 4.5 は grader サブエージェントと安価な分類器を走らせる。独自のコンテキスト窓を持ち、低コストで、verifier の役割に最適だ。

経済を成立させるパターン：オーケストレータは Fable 5、ワーカーは Sonnet 4.6、grader は Haiku 4.5、分類器ブロック時のフォールバックは Opus 4.8。

PART 2: 3つのプリミティブ

ステップ5：goal loop を選べ——/goal か Outcomes か

goal 駆動ループのためのほぼ同一なプリミティブが2つあり、ハーネスごとに1つずつ用意されている。形は同じ：独立した grader が作業をチェックし、「未達」の判定が次のイテレーションを起動し、grader が合格したらループが終了する。

作業が自分のマシン上で起き、明確な終了状態を持つ素早いセッション内ループが欲しいなら、Claude Code で /goal を使え。手を動かすコーディング、不安定なテストの撲滅、1ファイルの磨き込み。

作業がホストされたインフラ上でサンドボックスや GPU を使い、何時間も何日も走る必要があるなら、Claude Managed Agents で Outcomes を使え。ML 学習、長期の移行、何日もかかるリサーチ。ファイルベースのルーブリック、サブエージェント grader、ハードなイテレーション上限。

両者は同じ動きに依存している：コードを書いたエージェントが、それを採点するエージェントには決してならない。それがステップ6だ。

ステップ6：verifier サブエージェントを使え、決して自己批評するな

モデルは自分の作業を採点するのが下手だ。Claude Code チームは Fable 5 で直接それを確認した——verifier サブエージェントは self-critique に勝つ。

理由は努力ではなく構造的なものだ。自分の出力を判定するモデルは、自分の推論の軌跡が見えてしまい、自分がすでに書いたものに合致する結論を静かに贔屓する。

別のモデルは成果物とルーブリックしか見ない。作り手の物語に利害を持たない。その中立性こそが、価値の全てだ。

Anthropic 自身の実験では、独立した verifier を備えたバージョンのほうが、より大きな構造的変更を行い、失敗した実験を巻き戻すのではなく、それを乗り越えて最大の勝利へと押し進めた。自分を採点していたバージョンは、安全なスカラーを1つ調整し続け、早々に止まった。

この教訓を自分の設計に取り込め。本物の verifier があれば、Fable 5 はより広い空間を探索し、悪い中間結果からも回復する。それがなければ、最初の「まあ十分」を超えて押し進めるものが何もない。

ステップ7：Fable 5 に自分の Dynamic Workflow を書かせろ

Dynamic Workflows は、Claude にその場で自分のオーケストレーションハーネスを書かせる——汎用テンプレートではなく、タスクのために特注で組まれた、agent()・parallel()・pipeline() プリミティブを持つ小さな JavaScript ファイルだ。

プロンプトで "workflow" に言及すると、計画を組み立て、それを厳密な順序で従う。だから各段階があるべきときに走る。

ドキュメント化されたパターンのうち3つが、self-improving システムにおいて居場所を得る。

Fan-out-and-synthesize は作業を独立した断片に分割し、それぞれにエージェントを並列で走らせ、そして統合する。各断片が自分のクリーンなコンテキストに値するときに最適——たとえば Skill の各ルールを過去の例に対してテストするような場合だ。

Adversarial verification は、作り手ごとに独立した verifier を生成し、作り手の推論には一切触れさせない。これはステップ6をタスクごとに適用したものだ。

Loop-until-done は、停止条件に当たるまでエージェントを生成し続ける——新しい発見がない、残ったエラーがない、理論が確認された、など。/goal と組み合わせてハードなゴールラインを引け。

あと2つのパターン——classify-and-act と tournament——もあるが、複利ループには出番が少ない。前者はモデルルーティングに便利で、後者は命名やデザインのような好みベースのランキングに使える。

ステップ8：worktree を使って並列エージェントが衝突しないようにしろ

システムが2つ以上のエージェントを生成した瞬間、ファイルが衝突し始める。2つのエージェントが同じファイルに書くのは、2人のエンジニアが相談なしに同じ行をコミットするのと同じだ。

git worktree がこれを解決する——リポジトリの履歴を共有しつつ、独自のブランチ上にある別個の作業ディレクトリだ。だから一方のエージェントの編集が、もう一方のチェックアウトに文字通り触れられない。

作り手は worktree A に書く。verifier は worktree B で読むか、A に対して読み取り専用で走る。verifier がつついても、作り手の状態を壊すことは決してない。

並列実験では、各アーキテクチャ変更が自分の worktree で走る。オーケストレータがすべての結果を集め、勝者をマージする。失敗したブランチが他を汚染することは決してない。

Claude Code では worktree を3通りの方法で得られる：git コマンドを直接使う、セッションを自分のチェックアウトで開く --worktree フラグ、そしてサブエージェントに、後で自動でクリーンアップされる新しいチェックアウトを各ヘルパーに与える isolation 設定だ。

ステップ9：Routines を使ってノートパソコンを閉じたまま走らせろ

Routines は保存された Claude Code の設定——プロンプト、リポジトリ、コネクタ、権限——で、トリガーに応じて Anthropic 管理のクラウドインフラ上で走る。ノートパソコンの電源は切れていてよい。実行は依然として起きる。

Fable 5 にとって、これは「何日もまたぐ」能力を本当に活かす層だ。なぜならその持久力は、フルツール付きでローカルマシンの制限がないホスト型エージェント上で測られるものだからだ。本格的な GPU で何時間も必要な実行が、あなたのノートパソコンで起きることは決してない。

トリガーには3種類あり、それぞれが複利パターンに対応している。

Schedule トリガーは morning-briefing（朝のブリーフィング）パターンだ。毎日午前7時に、昨日の eval を再実行し、新しい失敗を Skills へ蒸留し、ダイジェストを投稿する。あなたが眠っている間にエージェントが鋭くなる。

API トリガーは fire-on-event（イベント発火）パターンだ。CI が失敗したら、Routine が調査する。アラートが来たら、Routine がトリアージする。システムがあなたの現実の環境に反応する。

GitHub トリガーは learn-from-real-work（実作業から学ぶ）パターンだ。PR が開かれたら、最新の Skills に対して評価する。マージされたら、新しいパターンを Skill へ書き戻し、リポジトリと Skill が同期を保つようにする。

PART 3: self-improvement の層

ステップ10：5段階の記憶の進行を理解しろ

エージェントの記憶を捉える最も役立つフレームは、5段階の進行だ。各段階が構造的な動きであり、モデルによって行き詰まる段階が異なる。

Stage 1 は fail（失敗）——エージェントが何かを間違え、後で役立つだけの十分な詳細とともにそれを文書化する。

Stage 2 は investigate（調査）——次へ進む前に、なぜその失敗が起きたのかを突き止める。

Stage 3 は verify（検証）——その診断を、推測ではなく確認済みの事実に変える。

Stage 4 は distill（蒸留）——その事実を、1つのケースを超えて適用される一般的なルールに変える。

Stage 5 は consult（参照）——次回は、ゼロから導き直す代わりにそのルールを読む。

モデルがどこに着地するかは鋭く異なる。Sonnet 4.6 はたいてい stage 1 で抜ける——めったに読み返さない失敗メモと未解決の推測の山だ。記憶は存在するが、決して複利的にならない。

Opus 4.7 は約 stage 3 に達し、おおよそ6回に1回検証する。Fable 5 は全進行を完了する傾向があり、最も強い実行では検証カバレッジが70%台に達し、将来の作業のための本物のルールを蒸留する。

ステップ11：5段階すべてを支える state file を作れ

進行はメンタルモデルだ。state file は、各段階の出力が実際に着地する場所だ。

Claude Managed Agents では、記憶はセッション間で生き残るマウントされたファイルシステムだ。Claude Code のローカルでは、markdown ファイルか Linear ボードが同じ仕事をする。

5段階それぞれが居場所を持つように構造化しろ。

このファイルが複利的に積み上がるか、ただ膨れ上がるだけかを決める運用ルールが2つある。

立ち去る前に書け。すべてのセッションは state file の更新で終わる——何を試したか、何が通ったか、何が失敗したか、どのルールが生き残ったか。終わりの書き込みがなければ、次のセッションはゼロから始まる。

セッション開始時に読め。すべての新しいセッションは、まず state file と関連する Skills を読むことで始まる。それを飛ばせば、Fable 5 でさえ Sonnet レベルの記憶挙動に逆戻りする。

ステップ12：学びを Skill に書き込め

state file はプロジェクトの記憶だ。Skills は手続き的記憶——プロジェクトをまたいで移動すべき「この種のことをどうやるか」だ。

パターンはこうだ：些細でない失敗のあとは必ず、その学びを Skill 自体に書き込む。Skill は走るたびに鋭くなる。

2週間複利的に積み上がってきた Skill は、まっさらなものとは似ても似つかない。新しいセクションが育つ——既知の失敗モード、ポストモーテムから生まれたルール、本番で見られたアンチパターン。それは静的な手順書であることをやめ、あなたが実際に学んだことの記録になる。

name: ci-triage

description: Classify CI failures, draft fixes for easy ones, escalate the rest.

CI triage skill

Classification rules

env: missing secret or wrong env var -> escalate, never auto-fix

flake: passes on retry, no code change -> retry once, then file

bug: deterministic, tied to recent commit -> draft fix

dependency: tied to a version bump -> draft rollback

infra: timeout, OOM, runner issue -> escalate

Known failure modes (added by the loop over 14 days)

webhook-race: e2e checkout flakes when Stripe webhook lands mid-test.

Fix: add a 2s settle delay in tests/utils/webhook.ts.

tls-handshake: Windows runners fail TLS 1.2 in PowerShell. Use bash.

db-migration: ALTER on a >1M-row table times out at 30s. Batch in 10k.

Anti-patterns (added after real incidents)

Never disable a failing test to make CI green. File it.

Never edit .github/workflows/ without human approval.

Never touch src/payments/ or src/billing/ without a security review.

Eval suite (step 13 - the loop verifies the skill)

Run against eval/ci-triage-cases.jsonl weekly. Any newly-failing case ->

add to known failure modes once the verifier confirms.

契約はシンプルだ。確認されたすべての学びは、state file だけでなく Skill にも入る。state file はプロジェクトとともに死ぬ。Skills はあなたの skills ディレクトリに生き、あなたとともに移動する。2週間の規律ある書き込みは、Fable 5 がまっさらなプロジェクトで冷えた状態から導き出すであろうものに勝つ Skill を生む。

ステップ13：vision で自分の UI を検証させろ

Fable 5 の目玉能力の1つが、vision を使って出力をゴールと照合することだ。それは抽象的に聞こえるが、何を置き換えるのかを見ればわかる——人間が UI が正しく見えるかをスクリーンショットを目を細めて確認する作業だ。Fable 5 はそのステップ自体を、ループの内側で、完了を宣言する前にやる。

作り手のサブエージェントが UI コードを書き、それをスクリーンショットにレンダリングする。

verifier のサブエージェントが vision でそのスクリーンショットを読み、ゴールと、あなたの Skill にあるデザイントークンと、state file にある前回のスクリーンショットと照合する。

判定がループに戻る。一致なら完了。不一致なら、ギャップを記述し、構造化された diff とともに作り手へ差し戻す。

これは、Fable 5 が自分の学習曲線のチャートを読み、その曲線が基準を満たしているかを判断したときに Anthropic が測定したのと同じ動きだ。チャートを読んだ人間はいない。verifier がチャートを読んだ。

ステップ14：Mythos の安全境界を前提に設計しろ

これは初日に飛ばして、後で代償を払うステップだ。

Fable 5 は、特定の高リスク領域で拒否する安全分類器を搭載して出荷される——サイバーセキュリティの脆弱性研究、生物学、化学、モデル蒸留だ。これらの領域では、Anthropic は自動的に Opus 4.8 へフォールバックする。これはバグではなく、ドキュメント化された挙動だ。

自律システムにとって、これは現実的な帰結を持つ。

あなたのシステムがセキュリティツール——SAST スキャン、エクスプロイトのロジック、一部のコードレビューさえ——に触れるなら、ブロックを覚悟しろ。フォールバックを前提に設計しろ：それらのタスクを意図的に Opus 4.8 へルーティングするか、ブロックを人間に見えるようにせよ。

生物・化学・蒸留の作業についても同じだ。網は広い。科学計算のワークフローが引っかかることもある。暗号プリミティブのレビューが引っかかることもある。

あなたの Skills がフォールバックを優雅に見せるようにしろ。Skill は、自分のどのタスクが分類器に当たる可能性があるかを知り、期待される挙動を文書化しておくべきだ。ブロックで静かに死ぬループは、本物のバグで死んだループと見分けがつかない——午後を1つデバッグに無駄にするまでは。

そしてデプロイ前にシステムカードを読め。それは分類器のスコープを文書化している。境界を失敗モードではなく既知のフォールバックとして扱えば、ポリシーが進化してもあなたのシステムは堅牢なままだ。

Fable 5 をその潜在能力の10%に留めてしまう間違い

コンテキストが増えただけの Sonnet 4.6 のように使うこと。5分のプロンプト＆クローズは、複利ゼロで Mythos 価格を燃やす。

独立した verifier を使う代わりに、自分の宿題を自分で採点すること。

state file がなく、毎セッションがゼロから再起動すること。Fable 5 の記憶アドバンテージの大半が消えるのがここだ。

決して書き込まれない Skills。静的な Skill は問題ない。だが本物の失敗のあとに学びを吸収しない Skill は、無駄になった足場だ。

Sonnet 4.6 で処理できる作業を Fable 5 で走らせること。複雑さでルーティングしろ。Fable 5 はオーケストレータの役割のために取っておけ。

長いセッションをノートパソコンで走らせること。何日もかかる作業にはクラウドが要る。閉じた蓋がセッションを殺す。

安全境界を無視し、分類器ブロックが静かな退行に変わること。

視覚的なタスクで vision 検証をしないこと。テキストだけの grader は、肝心の失敗を見逃す。

goal loop を飛ばし、実行が「完了」ではなく「まあ対処した」で止まること。

持ち帰るべき唯一のこと

Fable 5 はより速いチャットツールではない。複利的に積み上がるシステムのための基盤（substrate）だ。

能力の見出し——何日もまたぐセッション、サブエージェントへの委任、vision 自己チェック、蓄積された記憶——は、モデルの周りのシステムが自分の仕事をして初めて、その価格に見合う。

これを証明するすべての実験で、モデルは両側で同一だ。変わるのは、その周りのシステムだ。verifier。state file。eval ループ。

だから、まだやっていない層を1つ選べ——おそらく verifier サブエージェント、state file、あるいは vision 検証——そして明日それを追加しろ。それから次を追加しろ。

self-improvement はシステムの性質であって、モデルの性質ではない。さあ、システムを作れ。
