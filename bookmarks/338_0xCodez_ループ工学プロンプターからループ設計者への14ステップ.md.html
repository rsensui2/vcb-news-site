概要

Anthropic のエンジニアリングドキュメント・Addy Osmani のループ工学論考・各種計測研究を出典に、「手でプロンプトを打つ人」から「プロンプトする仕組みを設計する人」へ移行するための14ステップを3層で示した X Article（10,679 ブックマークの人気記事）。レバレッジの所在が "プロンプトを打つこと" から "プロンプトする仕組みを設計すること" へ移った、という主張が核。ただし *誇張せず*、「ループ工学は本物だが、ほとんどの開発者にはまだ要らない」と honest に線を引くのが特徴。

まとめ

  • 作る前に "4 条件テスト": ①タスクが（最低週次で）反復する ②検証が自動化されている（test/型/lint/build が落とせる）③トークン予算が無駄を吸収できる ④エージェントがシニア級の道具（ログ・再現環境・実行）を持つ。1つでも欠けるとループは元が取れない。
  • 得する人/損する人: 反復・機械検証可能・予算ありのチームは得。$20 の個人プランで重い検証ループを回すのは reckless。レビュー能力がボトルネックのチームはループでキューが伸びるだけ。
  • 5 つの構成要素: ①Automations（心拍＝スケジュール/イベント起動。Claude Code は /loop・scheduled tasks・Routines）②Worktrees（並列でファイル衝突を防ぐ）③Skills（プロジェクト知識を一度書き毎回読む）④Connectors（MCP で GitHub/Linear/Slack/Sentry に触る）⑤Sub-agents（maker と checker を分離＝Anthropic の evaluator-optimizer パターンの改名）。
  • 最小実用ループ: automation 1 + skill 1 + state file 1 + gate 1。順序——手動実行を安定 → skill 化 → loop 化 → schedule 化。指標は cost per accepted change（採択率が50%未満ならループは負け）。
  • 失敗モード: 「Ralph Wiggum ループ」（完了トークンを早く出して半端で抜ける）、ゴール・ドリフト（要約のたびに "Xするな" 制約が消える）、自己優遇バイアス、agentic laziness。対策はいずれも *客観的 gate と独立 verifier、再読する VISION.md/AGENTS.md*。
  • 2 つの隠れコスト: comprehension debt（理解していないコードが積もる）と cognitive surrender（考えるのをやめてループの出力を鵜呑み）。対策は技術でなく規律——diff を読む・gate を抜き取り検査・アーキ作業はループ禁止。
  • セキュリティ税: 無人ループ＝無人の攻撃面。未レビュー PR の自動マージ、skill 経由のプロンプトインジェクション（監査17,022件中520件が認証情報を漏洩）、ログへの secret 流出、権限のスコープ・クリープ（30日ごと再監査）。

日本語訳全文

ほとんどの開発者は、いまだにコーディングエージェントを手でプロンプトしている。打ち込み、待ち、diff を読み、また打ち込む。ビルダーの10人中9人は、エージェントを自分の代わりにプロンプトしてくれるループを一度も書いたことがない。

automation もなければ state file もなく、verifier もスケジュールもない。レバレッジの所在は移った——プロンプトを打つことから、プロンプトする仕組みを設計することへ。これは「プロンプター」から「ループ設計者」へ移るための14ステップ・ロードマップだ。

最新の AI alpha を得たければ私の LinkedIn をフォローして: linkedin.com/in/lev-deviatkin

これがその転換を成し遂げるための14ステップ・ロードマップ——出典は Anthropic のエンジニアリングドキュメント、Addy Osmani のループ工学に関する長文記事、そして最近の計測研究。

3つの層: 自分が本当にループを必要としているか見極め、5つの構成要素を学び、そして自分を傷つけずに済む最小のループを作る。

14ステップ。3層。プロンプトをやめろ。設計を始めろ。

PART 1 · なぜやるのか、そしてテスト

  1. ループ工学とは、プロンプターとしての自分自身を置き換えることだ。

この2年間、コーディングエージェントから何かを引き出す方法はこうだった: プロンプトを書き、コンテキストを共有し、返ってきたものを読み、次のプロンプトを書く。エージェントは道具であり、あなたはその間ずっとそれを握り続けていた。その時代は終わりつつある。

ループ工学とは、仕事を見つけ、それをエージェントに渡し、結果を確認し、何が起きたかを記録し、次の一手を決める——これを自律的にやる小さな仕組みを作ることだ。あなたはその仕組みを一度設計する。以後、その仕組みがエージェントをプロンプトする。

Addy Osmani はこれを6つの部分に分解している:

Anthropic のエンジニアは今や、2024年と比べて1日あたり8倍のコードをマージしている——ただしこの数字は Anthropic 自身が「真の生産性向上をほぼ確実に過大評価したもの」と呼んでいる。

この数字は議論の的だ。しかしメカニズムはそうではない: レバレッジの所在は、プロンプトを打つことから、プロンプトするループを設計することへ移った。

  1. 何かを作る前に 4 条件テストを走らせよ。

ループが元を取れるのは4つの条件下だ。1つでも欠ければ、ループは返ってくるものより高くつく。AlphaSignal の分析による honest な見解であり、ほとんどの X スレッドが飛ばす部分:

4つの条件を平易な言葉で:

タスクが反復する。ループはセットアップコストを多数の実行に分散して回収する。一度きりの仕事なら、良いプロンプトのほうが速くて安い。仕事が週次で再発しないなら、それはループではない——一度走らせたスクリプトだ。

検証が自動化されている。ループには、あなたが部屋にいなくても仕事を fail させられるものが必要だ。テストスイート、型チェッカー、リンター、ビルド。自動チェックがなければ、あなたは再び椅子に座ってあらゆる diff を読むことになる——それこそループが取り除くはずだった仕事そのものだ。

トークン予算が無駄を吸収できる。ループはコンテキストを再読し、リトライし、探索する。実行が何かを出荷するかどうかに関わらず、それはトークンを燃やす。この技術は予算に応じてスケールする。だからこそ、トークンが実質無料の人には自明に見え、従量課金プランの人には reckless に見える。

エージェントがシニアエンジニアの道具を持っている。ログ、再現環境、書いたコードを実行して何が壊れるか確認できる能力。それがなければ、ループは目隠しで反復する。

  1. 誰が勝ち、誰が負けるか。ループは支出できる者に味方する。

経済性は普遍的ではない。ループ工学を「自明」と呼ぶ人々は、たいてい従量課金でないトークンを持っている。

それが「reckless」になる人々は、たいてい $20 の消費者向けプランで、上限超過や予想外の請求にぶつからずに重い検証ループを回そうとしている。

実際に恩恵を受けるのは誰か:

反復的で機械チェック可能な仕事と、それを回す予算を持つチーム——継続的なテストトリアージ、依存関係の更新、lint-and-fix パス、強力なテストカバレッジを持つコードベースでの issue から PR へのドラフト作成。

強力な既存テストスイートを持つコードベース。ジュニアエンジニアがチェックリストからこなせるタスクで、ミスをテストスイートが捕まえられるなら、ループは適合する。

すでにマルチエージェントパターンを使っている async-first なチーム。こうしたチームにとって、routines は欠けていたオーケストレーション層だ。

今は見送るべきは誰か:

消費者向けプランのソロビルダー——生産性向上より先にトークンの請求書が届く。

自動検証のないコードに取り組んでいる人。本物のチェックがないループは、エージェントが自分自身に繰り返し同意しているだけだ。

本当の制約が、タイピング速度ではなくレビュー能力にあるチーム。ループはより多くのコードを生む。レビューがすでにボトルネックだったなら、キューを長くするだけだ。

一度きりのタスク、探索的な仕事、あるいは「完了」が判断を要するものについては、今でも狙いを定めた1つのプロンプトのほうが勝つ。この記事の honest なバージョンはこうだ: ループ工学は本物だが、ほとんどの開発者にはまだ要らない。

  1. 30秒ループチェック。

ステップ2の4条件テストは戦略的な意思決定だ。これは戦術的なほう——特定のタスクをループにする前に走らせるチェックリストだ。

1つでも外したら、手動プロンプトのままにしておけ。

  1. タスクが少なくとも週次で起きる。週次未満 → セットアップコストは決して回収されない。
  2. テスト、型チェック、ビルド、またはリンターが悪い出力を却下できる。自動 gate がない → エージェントが自分の宿題を採点する。
  3. エージェントが変更したコードを実行できる。再現環境がない → 反復は目隠しだ。
  4. ループにハードストップがある。トークン予算、反復回数、または時間制限。それがなければ、誰かが請求書に気づくまでループは走り続ける。
  5. マージ・デプロイ・依存関係変更の前に人間がレビューする。不可逆なものはすべて、アクションの前に人間の承認 gate が必要だ。

良い最初のループ:

CI failure triage——夜次で、失敗をスキャンし、原因を分類し、簡単なものについて修正 PR をドラフトする。

依存更新 PR——週次で、更新をスキャンし、互換性をテストし、PR を開く。

lint-and-fix パス——PR オープンのイベントごとに、スタイル修正を自動適用する。

flaky test の再現——ある仮説がテストを生き残るまでループする。

強力なテストを持つコードでの issue から PR へのドラフト作成。悪い出力はスイートに却下される。

悪い最初のループ——これらは人間が椅子に座る必要がある:

アーキテクチャの書き直し

認証や決済のコード

本番デプロイ

曖昧なプロダクト作業

「完了」が判断を要するものすべて

PART 2 · 5つの構成要素

  1. Automations: 心拍。

Automations こそが、ループを実際のループにし、一度やった単発の実行ではなくするものだ。スケジュール、イベント、またはトリガー条件で発火する。それらは心拍——ループの他のすべてがそこにぶら下がっている。

重要な2つのツールでこれがどう見えるか:

Codex。Automations タブ——プロジェクトを選び、プロンプトを設定し、頻度を設定し、ローカルチェックアウトかバックグラウンド worktree かを選ぶ。何かを見つけた実行は Triage インボックスに届く。何も見つけなかった実行は自分自身をアーカイブする。

Claude Code。同じ形に組み合わさる3つのプリミティブ:

セッションスコープの頻度には /loop、再起動を生き残るには Desktop の scheduled tasks、ラップトップを閉じたままのクラウド実行には Routines。ライフサイクルイベント用に hooks と組み合わせる。

動くループと高くつくループを分ける、automation 内の2つのプリミティブ:

/loop は頻度に応じて再実行する。state に関わらず定期的なチェックが欲しいときに使う。

/goal はあなたが書いた条件が実際に真になるまで続ける。別の小さなモデルが完了を確認するので、コードを書いたエージェント自身が採点するわけではない。

これは maker-vs-checker の分離を、停止条件そのものに適用したものだ。

  1. Worktrees: 混沌なしの並列。

2つ以上のエージェントを走らせた瞬間、ファイルが衝突し始める。2つのエージェントが同じファイルを書くのは、2人のエンジニアが相談せずに同じ行にコミットするのと同じ頭痛だ。

git worktree がそれを解決する——同じリポジトリ履歴を共有しつつ、独自のブランチ上にある別個の作業ディレクトリ。だから一方のエージェントの編集は、もう一方のチェックアウトに文字どおり触れられない。

両ツールでどう現れるか:

Codex は worktree サポートを組み込んでいる——複数のスレッドが互いにぶつからずに同じリポジトリに同時にアクセスする。

Claude Code は git worktree を直接公開し、セッションを独自のチェックアウトで開く --worktree フラグ、そして各ヘルパーが終了後に自己クリーンアップする新鮮なチェックアウトを得るための subagents 上の isolation: worktree 設定を提供する。

worktree は機械的な衝突を取り除くが、あなた自身が依然として上限だ。実際に何個の並列エージェントを走らせられるかは、ツールではなく、あなたのレビュー帯域が決める。

  1. Skills: プロジェクト知識を一度書く。毎回読む。

Skill とは、金魚のように毎セッション同じプロジェクトコンテキストを説明し直すのをやめる方法だ。両ツールは同じフォーマットを使う: 中に SKILL.md を持つフォルダ。指示とメタデータを保持し、オプションでスクリプト・参照・アセットを持つ。

これがループにとって特に重要な理由: skill のないループは、サイクルごとにプロジェクトコンテキスト全体をゼロから再導出する。skill があれば、意図が複利で積み上がる。

規約、ビルド手順、「あの一件があったからこういうやり方はしない」——一度外側に書けば、毎回の実行で読まれる。

  1. Connectors: ループがあなたの本物の道具に触れる。MCP 経由で。

ファイルシステムしか見えないループは、ちっぽけなループだ。Model Context Protocol (MCP) の上に構築された Connectors は、エージェントに issue トラッカーを読ませ、データベースをクエリさせ、ステージング API を叩かせ、Slack にメッセージを落とさせる。

Codex も Claude Code も MCP を話すので、一方のために書いた connector はたいていそのまま他方でも動く。

これが、「これが修正です」と言うエージェントと、PR を開き、Linear チケットをリンクし、CI がグリーンになったらチャンネルに ping するループとの違いだ。

connectors こそ、ループが「できればこうするのに」と告げるだけでなく、あなたの実際の環境の中で行動できる理由だ。

ループ作業に対して最も速く元を取る connectors を、順に:

GitHub——リポジトリを読み、ブランチを作り、PR を開き、issue にコメントし、webhook イベントに反応する。あらゆるコードループにとって最大の初日の勝利。

Linear または Jira——ループが進むにつれてチケットを更新し、PR を issue にリンクし、検証が通ったらアイテムを自動でクローズする。

Slack——トリアージ結果を投稿し、エスカレーション時に人間に ping し、夜間の実行を朝に要約する。

Sentry / あなたのエラートラッカー——ループにライブアラートを調査させ、高頻度のものについて修正をドラフトさせる。

  1. Sub-agents: maker を checker から遠ざけておく。

ループの中で構造的に最も有用なものは、群を抜いて、書くエージェントとチェックするエージェントを分けることだ。

Osmani の表現は的確だ: コードを書いたモデルは「自分の宿題を採点するには優しすぎる」。異なる指示を持ち、時には異なるモデルを使う2つ目のエージェントが、1つ目が自分を言いくるめて通したものを捕まえる。

これは Anthropic の2024年12月のエンジニアリング記事にある evaluator-optimizer パターンの、新しい名前での再登場だ。1つのモデルが生成し、別のモデルが批評し、繰り返す。2026年にバズった語彙は、18ヶ月前に文書化されていた。

両ツールで sub-agents がどう着地するか:

Codex はあなたが頼んだときだけ subagents を生成し、同時に走らせ、結果を1つの答えに畳み込む。あなたは自分のエージェントを .codex/agents/ 内の TOML ファイルとして定義する——名前、説明、指示、オプションでモデルと推論努力。

セキュリティレビュアーは高努力の強いモデルにでき、エクスプローラーは何か速い read-only なものにできる。

Claude Code は .claude/agents/ 内の subagents と、互いに仕事を受け渡す agent teams で同じことをする。

よくある分割: 1つのエージェントが探索し、1つが実装し、1つが spec に対して検証する。

ループの中で特にこれが重要な理由: ループはあなたが見ていない間に走るので、あなたが実際に信頼できる verifier こそが、その場を離れられる唯一の理由だ。

sub-agents はそれぞれが自分のモデルとツール作業を行うので、より多くのトークンを燃やす——セカンドオピニオンに支払う価値のあるところに使え。

PART 3 · 正しく作るか、作らないか

  1. state file。エージェントは忘れる。ファイルは忘れない。

これは、重要視するにはあまりに馬鹿げて聞こえるが、実はあらゆる動くループの背骨であるピースだ。マークダウンファイル、Linear ボード、JSON state——単一の会話の外側に存在し、何が済んで何が次かを保持する何か。

これが重要な理由: エージェントはデフォルトで記憶が短い。今セッションで学んだことは、書き留めない限り明日には消える。

Osmani のルール: エージェントは忘れる、リポジトリは忘れない。永続的な state のないループは毎回の実行でリスタートする。state のあるループは再開する。

state file がどこに存在するかの2つのパターン:

リポジトリ内のマークダウン——ルートか .claude/ 内の STATE.md。バージョン管理される。シンプル。diff で読める。ソロまたは小チームの作業に最適。

外部システム（Linear、GitHub Issues、データベース）——リポジトリをまたいで生き残り、クエリ可能で、チーム全体の可視性をサポートする。複数の人間がループの動きを見る必要がある本番ループに最適。

ゴールから逸れるリスクのある長時間ループには、state file を、エージェントが毎回の実行で読み直す常設の高レベル spec——VISION.md か AGENTS.md——と組み合わせる。state はエージェントに「今どこにいるか」を伝える。spec は「どこへ向かうか」を伝える。

  1. 最小実用ループ。

ステップ2の4条件テストに合格したなら、何か凝ったものの前に、動く最小のループを作れ。4つの部分、群れ（swarm）なし。

4つの部分を平易な言葉で:

1つの automation。頻度で発火し、明確な条件で停止するスケジュール実行。Claude Code の /loop か Codex の automation を使う。述べた条件が成立するまで走らせたいときは /goal と組み合わせる。

1つの skill。エージェントが毎回ゼロから再導出するであろうプロジェクトコンテキストを保存する、単一の SKILL.md。

1つの state file。何が済んで何が次かを記録するマークダウンファイルか Linear ボード。明日の実行はリスタートではなく再開する。

1つの gate。悪い仕事を自動で fail させるテスト、型チェック、またはビルド。これがループが助けになるか、ただ浪費するだけかを決める部分だ。

順序が重要だ: まず手動実行を1回信頼できるものにする。それを skill にする。ループで包む。それからスケジュールする。先に飛ばすのが、本番でループが失敗する原因だ。

重要な指標は cost per accepted change（採択された変更あたりのコスト）だ——費やしたトークンでも、試みたタスクでも、スケジュールしたループでもない。採択率が50%未満なら、ループが省いてくれるはずだったレビュー作業をあなたがやっており、ループは負けている。

  1. Ralph Wiggum ループ。静かに失敗するループ。

エンジニアの Geoffrey Huntley がこの失敗モードを文書化し、名付けた。完了したときにだけ完了トークンを出すはずのエージェントが、それを早く出してしまい、ループは半端な仕事で抜ける。ハード gate がなければ、ループは静かに失敗し、浪費し続ける。

Ralph Wiggum ループとは、次のことが起きたときに発生する:

本物の verifier がない。ただ「レビューして」と頼まれた2つ目のエージェントだけで、客観的なシグナルがない。2人の楽観主義者が同意しているだけ。

ソフトな完了条件。「完了」がテスト・ビルド・型チェックではなく、エージェントの判断で定義されている。

ハードストップがない。成功が検証されるまでではなく、何か外部のもの（レート制限、あなたが気づくこと）が止めるまでループが続く。

修正策はステップ11の gate だ——仕事を fail させられる客観的な何か。通るか落ちるかのテスト。コンパイルするかしないかのビルド。ゼロか非ゼロを返すリンター。意見を持つ verifier ではない。

知っておく価値のある、計測された他の失敗モード:

長いセッションでのゴール・ドリフト。各要約ステップは情報を失う（lossy）。「Xするな」という制約は47ターン目で消える。緩和策: 毎回の実行で読み直される常設の VISION.md か AGENTS.md。

自己優遇バイアス。コードを書いたエージェントは自分の宿題を採点するには優しすぎる。緩和策: maker の推論にさらされていない、別個の verifier subagent。

agentic laziness（エージェント的な怠惰）。ループが部分完了の時点で「十分に完了」と宣言する。緩和策: 新鮮なモデルがチェックする客観的な停止条件付きの /goal。

  1. comprehension debt と cognitive surrender。

これは、ループが悪くなるときではなく、良くなるときにこそ鋭くなる失敗モードだ。Osmani のエッセイから来る、名前のついた2つのリスク:

comprehension debt（理解の負債）。ループがあなたの書いていないコードを速く出荷するほど、リポジトリが含むものと、あなたが理解しているものとの距離が大きくなる。痛い請求書はトークンの請求書ではない。チームの誰も読んでいないシステムをデバッグしなければならない日だ。

cognitive surrender（認知的降伏）。意見を形成するのをやめ、ループが返すものを何でも受け入れたくなる引力。ループを設計することは、判断を持ってやれば治療薬になり、考えるのを避けるためにやれば促進剤になる。同じ行動、正反対の結果。

緩和策は技術的なものではない:

diff を読め。ループが出荷するものを読まないなら、あなたは複利の利息で comprehension debt を借りている。

gate を抜き取り検査せよ。ループが開いた PR をいくつか選び、それを承認したテストが、あなたが気にする失敗モードを実際に捕まえているか検証する。gate は腐る。

ループをアーキテクチャ作業から締め出せ。小さく機械チェック可能な変更に留めておく。判断を要するものに触れさせた瞬間、comprehension debt が加速する。

ループをチームメイトとペア設計せよ。ループを設計するときの2つ目の目が、さもなければループが永遠に突くであろう盲点を捕まえる。

  1. セキュリティ税。無人のループは無人の攻撃面だ。

無人で走るループは、無人で走る攻撃面でもある。

あなたのループが防御しなければならない脅威モデル:

生成コードが未レビューで出荷される。ループは人間が読めるより速く PR を開く。セキュリティチェック（SAST、依存関係監査、シークレットスキャン）を含む gate がなければ、安全でないコードが自動でマージされる。

注入ベクトルとしての skills。skills を自動インストールするループは、それらの説明に潜むあらゆるプロンプトインジェクションを継承する。インストール前に skill のソースを監査せよ。

ログ内の認証情報。長時間ループ中のデバッグログは、あなたが監視していないログ全体に secret を撒き散らす。本番ループでは冗長ログを無効にする。ログに残るものはサニタイズする。

権限のスコープ・クリープ。read-only 権限でテストされたループに、利便性のために「たった1つ」の書き込み権限が追加され、その後一度も再監査されない。30日ごとに権限を再監査せよ。

§ ループを金食い虫に変える失敗

4条件テストを走らせずにループを作ること。ステップ2には理由がある。ほとんどの開発者は少なくとも1条件で失格する。

客観的な gate がない。テスト・型チェック・ビルドなしで「レビューして」と頼まれた2つ目のエージェントは、ただの2人目の楽観主義者だ。

1つのエージェントが書くことと検証することの両方をやる。自己優遇バイアス。maker が自分の宿題を採点し、いつも「A+」だ。

state file がない。明日の実行が再開ではなくゼロからリスタートする。

曖昧な停止条件。「良さそうに見えたら完了」は決して成立しない。テスト、型パス、または通るビルドを使え。

トークン予算の上限がない。ループはコンテキストを再読し、リトライする。上限がなければ、野心的なループは予想の5〜10倍のトークンを燃やす。

消費者向けプランで重い検証を伴うループを走らせること。トークンの請求書かレート制限、どちらかがあなたを捕まえる。

コミュニティ skills を自動インストールすること。監査された17,022件の skills のうち520件が認証情報を漏洩している。インストール前にソースを読め。

判断を要する仕事でのループ。アーキテクチャ、認証、決済、曖昧なプロダクト判断。ループは戦略ではなく lint-and-fix に留めておけ。

diff を読まないこと。複利の利息での comprehension debt。誰も読んでいないシステムをデバッグする日は、トークンがかつてかかった以上に高くつく。

結論:

レバレッジは移った。あなたの仕事もだ。

この2年間、コーディングエージェントと働く上でのレバレッジはプロンプトにあった。より良いプロンプト、より良いコンテキスト、より良いワンショット出力。

その段階は終わりつつある。エージェントは十分に良くなり、次のレバレッジの所在は一階上にある: 何に・いつ・どの gate で取り組むかを決め、実行と実行の間にどの state が生き残るかを決める仕組みだ。

だがこの物語の honest なバージョンは、誰もがループを作ろうと急ぐべきだということではない。ほとんどの開発者にはまだ要らない——タスクが反復し、検証が自動化され、予算が無駄を吸収でき、エージェントがシニアエンジニアの道具を持つまでは。

1条件でも欠ければ、ループは返ってくるものより高くつく。

テストに合格したなら、小さく作れ。1つの automation。1つの skill。1つの state file。1つの gate。手動実行を1回信頼できるものにする。それを skill にする。ループで包む。それからスケジュールする。順序が重要だ。先に飛ばせば、誰も理解していない仕組みに支払うことになる。

Cherny の論点は、仕事が楽になったということではない。レバレッジの所在が移った、ということだ。ループを作れ。エンジニアであり続けろ。
