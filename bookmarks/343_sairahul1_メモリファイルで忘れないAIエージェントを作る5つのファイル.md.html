メモリファイルで「忘れない」AIエージェントを作る — 5つのファイル構成

№080 / 487 SRCx.com/sairahul1 ↗ GHGitHub ↗
080BOOKMARK / 487

有益度: ⭐⭐⭐⭐

エンゲージメント: Likes 253 / RT 44 / Replies 16 / Bookmarks 772 / Views 391,817

概要

「AIエージェントが失敗するのはモデルが悪いからではなく、毎セッション記憶喪失で目覚めるから」という問題提起から、CLAUDE.md / AGENTS.md / CLAUDE.local.md / MEMORY.md / README.md の5ファイルでエージェントに永続メモリを与える設計を解説した X Article。

まとめ

  • 失敗の真因は「モデルの賢さ」ではなく、モデルの下にあるメモリ層の欠如。プロンプト→実行→セッション終了→記憶消失→次回も同じミス、という繰り返しが AI コーディングで最大の時間浪費。
  • 5ファイルの役割分担:

- CLAUDE.md — Claude 専用の briefing。プロジェクト文脈/コード規約/コマンド/アーキテクチャの4節、目標300行未満。

- AGENTS.md — ベンダー横断の標準。Cursor / Copilot / Gemini CLI / Windsurf / Aider / Zed なども読む共通ファイル。

- CLAUDE.local.md — 個人の好み。git にコミットしない。

- MEMORY.md — AI が自分で書く自動メモ（index は毎セッション読み込み）。

- README.md — 人間向け（エージェント向けではない）。

  • @imports で巨大1枚岩を回避（最大5階層、チームごとに分割所有）。
  • Auto-memory が最新かつ最重要層: Claude Code がセッション中に自分でメモを書く。/memory でレビュー、「今日学んだことをメモに反映して」で発火。
  • 結論の式: Model + Memory + Retrieval + Feedback = Useful Agent。記憶こそ複利で効く変数で、モデルの賢さは複利でない。

日本語訳全文

ほとんどのAIエージェントが失敗するのは、モデルが悪いからではない。

毎セッション、記憶喪失の状態で目覚めるからだ。

あなたは Claude にこう言う。「うちは npm じゃなく pnpm を使う」

次のセッション: また npm を使おうとする。

「ここではデフォルトエクスポートは使わない」と言う。

次のセッション: デフォルトエクスポートを書く。

あなたが入れた修正は、セッションが終わった瞬間に蒸発する。

これには「1ファイルで効く解決策」がある。

それを見つけるのに、同じことを繰り返し言い続けて3ヶ月かかった。

学んだことを全部ここに書く。

なぜ大半のAIエージェントは失敗するのか

モデルのせいではない。

モデルの「下」にある層が欠けているせいだ。

→ プロンプトを書く

→ エージェントがタスクを実行する

→ セッション終了

→ 記憶が消える

→ 次のセッション: 同じミス

→ 同じ指示を繰り返す

→ 永遠に

このループこそ、AIコーディングで時間を浪費する最大の発生源だ。

悪いコードでもハルシネーションでもない。

「繰り返し」だ。

欠けている層: メモリ

誰もが「どのモデルが一番賢いか」に取り憑かれている。

層を間違えている。

本当のアップグレードは、より賢いモデルではない。

モデルに「学んだことを保存する場所」を与えることだ。

→ プロンプト → エージェントに「今やるべきこと」を伝える

→ エージェント → タスクを実行する

→ メモリ → セッションを跨いで文脈を保持する

→ 永続的な文脈 → 修正の繰り返しが消える

→ 学習システム → エージェントが実際に時間とともに改善する

これが「ツール」と「チームメイト」の違いだ。

ツールは毎回ゼロから、言われたことをやる。

チームメイトは昨日を覚えている。

すべてのAIエージェントに必要な5つのメモリファイル

メモリが欠けている層だと受け入れたら、次の問いは「それはどこに置くのか」。

5つのファイル。それぞれ別の役割。

→ CLAUDE.md — Claude 個人への briefing 文書

→ AGENTS.md — 全主要ツールが読む普遍的標準

→ CLAUDE.local.md — 個人の好み。git にはコミットしない

→ MEMORY.md — AI が自分について自動で書くメモ

→ README.md — エージェントではなく人間のため

順に見ていこう。

CLAUDE.md — すべての始まり

これをプロジェクトのルートに置く。

Claude は毎セッションの冒頭でこれを読む。

記憶喪失の新メンバーへの briefing 文書だと思えばいい。

良い CLAUDE.md は4つの節を持つ:

→ プロジェクト文脈 — 一行。「Stripe と Postgres を使った Next.js の EC アプリ」

→ コードスタイル — 「ちゃんとフォーマットして」ではなく「ES modules、named export、インデント2スペース」

→ コマンド — 正確な文字列。「テストを実行」ではなく pnpm test:integration

→ アーキテクチャ — 「API ルートは /src/api/[resource]/route.ts。DB アクセスは Repository パターン」

目標: 300行未満。

すべての行が、実際の作業と「注意」を奪い合う。

/init を実行すれば Claude が雛形を自動生成する。

そして大半を削れ。

デフォルトのファイルには、Claude が package.json から既に分かることまで入っている。ファイルが無いと Claude が間違えること「だけ」を残せ。

@imports システム — 軽量に保つ

CLAUDE.md がすべてを抱える必要はない。

他のファイルを import できる:

See @README.md for project overview

See @docs/api-patterns.md for API conventions

See @package.json for available npm scripts

import は再帰的にできる — 最大5階層。

これで「1つの巨大ファイル」問題が解ける。

チームの場合: フロントエンドチームは docs/frontend-rules.md を所有。

セキュリティは docs/security.md を所有。

CLAUDE.md はそれらを全部 import するだけ。

ルートファイルは1つ、専門ソースは多数。

AGENTS.md — 普遍的標準

CLAUDE.md は Claude にしか効かない。

チームが Cursor、Copilot、Gemini CLI も使うなら — 彼らはそれを読まない。

AGENTS.md がこれを解決する。

1ファイル。すべての主要エージェントが読む。

Claude Code、Cursor、GitHub Copilot、Gemini CLI、Windsurf、Aider、Zed、Warp などが対応。

標準的な Markdown。特別なスキーマも YAML も不要。

AIエージェントのための README だと思えばいい。

README.md は人間向け。AGENTS.md はベンダーを問わず全エージェント向け。CLAUDE.md はその上に Claude 固有の追加分を載せる。

これらは補完関係で、競合ではない。

Auto-memory — 自分でメモを取るAI

これが最新かつ最も興味深い層。

Claude Code は今やセッション中に自分でメモリファイルを書く。

memory/

├── MEMORY.md ← index、毎セッション読み込み

├── debugging.md ← デバッグのパターンのメモ

├── api-conventions.md ← API 設計の決定

└── ...

鍵となる転換:

あなたが CLAUDE.md を書く。あなたが指示を与える。

Claude が MEMORY.md を書く。学んだことを記録する。

→ 人間がルールを書く

→ エージェントが作業しながらパターンを発見する

→ エージェントが自分のメモリを書く

→ 将来のセッションがより賢く始まる

これは直接トリガーできる。生産的なセッションの終わりにこう言うだけ:

「今日うちのコードベースについて学んだことをメモリファイルに反映して」

学びが永続する。カスタム ORM ラッパーを5回目の説明をしなくて済む。

/memory でいつでも、Claude が保存した内容をレビュー・編集できる。

「/init してから削る」ワークフロー

新規プロジェクトでメモリファイルを最速で立ち上げる方法:

プロジェクトディレクトリで /init を実行

Claude がコードベースを基に CLAUDE.md の雛形を生成

要らないものを削る

ステップ3でほとんどの人が間違える。

生成されたファイルは下書きであって完成品ではない。

よく余計なものが入る。「このプロジェクトは JavaScript を使う」— どうも、package.json を見れば分かる。

妥当な下書きから削っていく方が、白紙から書くより良い。

セットアップ後は、有機的に育てる。

Claude が間違った前提を置いたら — 例えば非推奨パッケージを import し続けるなら — 一度だけ直すのではなく、

こう言え: 「CLAUDE.md に追記して: 常に @company/utils ではなく @company/utils-v2 から import する」

その指示は将来の全セッションで永続する。

数週間ごとに、Claude に CLAUDE.md をレビュー・整理させる。

指示は溜まる。冗長になるものも、矛盾し始めるものもある。一掃すれば鋭さを保てる。

私の実際のセットアップ

複数の本番プロジェクトで全部試した結果、定着したのはこれ:

→ AGENTS.md をルートに — どの AI ツールも読む共有指示。ビルドコマンド、コード規格、テスト要件。

→ CLAUDE.md は @imports で Claude 固有の挙動。100行未満を維持し、ほぼ docs/ ファイルへのポインタ。

→ CLAUDE.local.md は個人の癖 — テストデータ、サンドボックス URL、ショートカット。git にはコミットしない。

→ Auto-memory 有効。Claude が自分でメモを取る。月次でレビュー。

→ それ以外は全部、AGENTS.md を指す symlink に置き換え。単一の真実ソース。

エレガントではない。

だがチームの全ツールで「指示のドリフト」を殺せる。

より大きな転換

ほとんどの開発者はこう考える:

良いモデル = 良いエージェント。

間違い。

本当の式:

Model + Memory + Retrieval + Feedback = 有用なエージェント

メモリの無い賢いモデルは、明日もテストコマンドを忘れる。

優れたメモリを持つ並のモデルは、毎週鋭くなる。

メモリは複利で効く変数だ。

モデルの知能は違う。

私が AI ワークフローに加えた最大の改善は、モデルを切り替えたことではなかった。

モデルにメモリを与えたことだ。

「Claude、うちは pnpm を使う」を毎セッション言うのと、

「Claude はもう知っている」を毎セッション、の違い。

それが「ツール」と「チームメイト」の違いだ。
