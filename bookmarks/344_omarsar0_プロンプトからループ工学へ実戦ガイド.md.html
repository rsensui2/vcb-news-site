プロンプトから「ループ工学」へ — 本番で動くエージェントループの実戦ガイド

概要

「もうエージェントにプロンプトを打つな、エージェントにプロンプトを打つループを設計しろ」という最近の主張（Peter Steinberger / Boris Cherny）を、抽象論で終わらせず「ループとは何か・なぜ重要か・本番でどう作るか」まで落とした実践版の X Article。DAIR.AI の elvis（@omarsar0）執筆。

まとめ

  • ループ工学＝作業が1段上がる: 「コードを書く」から「コードを書くシステムを書く」へ。先行者は IDE を開かず月に数百 PR を出すと報告。
  • 「ループ」は最低5つの意味: ReAct(2022) → AutoGPT(2023) → ralph loop（反復間の context リセット）→ /loop・/goal（完了条件を内蔵）→ orchestration（多エージェントの fan-out）。
  • ループを構成する6部品: ①trigger ②isolation（git worktree）③written-down context ④tools へのreach ⑤独立した検証者 ⑥disk上のstate。
  • 具体例 "PR babysitter": 15分毎 / agent-watch ラベルの開いた PR / CI が決定的理由で赤なら1回修正・main がズレたら1回 rebase / 予算1試行5分10ファイル / CI緑か予算切れで停止して人間に ping。
  • Claude Code の /goal: 終了状態・証拠・制約・予算の4つを契約のように明示。
  • コストの所在: 単発呼び出しではなく「ループが何周するか」。弱い検証者が最も高コストなバグ。
  • ループにすべきでない時: 一発で終わる編集 / 未スコープの探索 / 安価な自動チェックが無いもの。

日本語訳全文

AIコーディング界隈である主張が広まっている。「コーディングエージェントにプロンプトを打つのをやめ、エージェントに代わってプロンプトを打つループを設計し始めろ」。新しいものは何でもそうだが、これは頻繁に繰り返される割にめったに説明されない。これがその実践版だ。エージェントループとは何か、なぜ重要か、本番でどう見えるか。

以下は、学生・技術系の創業者・AIエンジニア・スタートアップとの会話から得た私の考え（Claude の助けを借りて書いた）だ。

この主張の出どころ

「もうコーディングエージェントにプロンプトを打つべきではない。エージェントにプロンプトを打つループを設計すべきだ」— Peter Steinberger (@steipete)、2026年6月7日、220万 views。

Boris Cherny（Claude Code の生みの親）が反対側から同じ点を突く。

「私はもう Claude にプロンプトを打たない。走っているループがある。それらが Claude にプロンプトを打ち、何をすべきか判断する。私の仕事はループを書くことだ」— Boris Cherny (@bcherny)。

要点は「プロンプトエンジニアリングが死んだ」ではない。ループ工学では、作業が1段上に移る。コードを書くことから、コードを書くシステムを書くことへ。この道を最も進んだ開発者は、IDE を開かずに月に数百の PR を出荷し、全行がエージェントによって書かれたと報告する。

ループとは実際に何か

ループとは、あなたが書く小さなプログラムで、4つのことをする:

代わりにコーディングエージェントにプロンプトを打ち、

それが生成したものを読み、

完了したか判断し、

そうでなければエラーや次のステップで再びプロンプトを打つ。

あなたはループの中に座ってプロンプトを打つのをやめる。ループを書き、モデルはそれが呼び出すサブルーチンになる。

形は常に同じ: ゴールを設定し、行動し、チェックし、エラーを戻し、チェックが通るかループが自分で止まるまで繰り返す。

「ループ」は最低5つの意味を持つ

意見の食い違いの多くは、1つの単語を5つの異なる概念に使っているせいだ。古い順に並べる。

  • ReAct (2022): 元の研究パターン。推論・行動・観察・繰り返し。
  • AutoGPT (2023): 自己プロンプトのゴールループ。止め時を知らないことで悪名高い。
  • ralph loop: 反復間で意図的に context をリセットし、エージェントが自分の履歴で溺れないようにする。
  • /loop と /goal: カデンスと完了条件がエージェントに組み込まれ、turn を跨いで state を運ぶ。
  • orchestration: 1人の作者が多数のエージェントを fan-out し、GitHub・Slack・チャットを読んで次に何を作るか決める。

実際に組み立てる部品

進化の系譜は「ループという言葉で人が何を指すか」を説明する。次は「ループが何から作られるか」。同じ6部品が毎回現れ、今やそのほとんどは自分で保守するカスタムスクリプトではなく、コーディングツールに内蔵されて出荷される。

  • トリガー: あなたが「実行」を押さなくてもループを始める何か。スケジュール、webhook、ファイル変更、PR にラベルが付く、など。これが「手で繰り返す単発実行」と「本物のループ」を分ける。
  • 隔離（Isolation）: エージェントごとの private なチェックアウト、通常は git worktree。同時に走る2つのエージェントが互いのファイルを上書きできないように。2つ以上走らせたら、これは必須になる。
  • 書き留めた context: 規約・ビルド手順・プロジェクト固有のルールを、エージェントが毎回読む場所に置く。省くと、ループは毎周プロジェクトをゼロから再導出し、隙間を推測で埋める。
  • ツールへの reach: issue tracker・CI・DB・チャットへのコネクタ。ループが PR を開き、チケットを紐付け、結果を投稿できるように。修正を出力して人間が運ぶのを待つのではなく。
  • 2番目のエージェントがチェックする: 出力を採点する別のワーカーを、生成したものから切り離す。自分の仕事をレビューするモデルはほぼ全部を通してしまうからだ。
  • disk 上の state: Markdown ファイル、ボード、キューなど、何が終わって何が次かを記録する会話の外側の何か。モデルは実行間で忘れるが、ファイルは忘れない。

この6つを組み立てれば、ループ工学の良い出発点になる。以前は全部手で組んでいたが、今やほとんどが内蔵機能として出荷され、だからこのパターンは周縁の技術から一般的な利用へと移った。

具体的なループ「PR の子守（babysitter）」

今日作れる具体例:

  • トリガー: 15分ごと。
  • スコープ: agent-watch ラベルの付いた開いた PR。
  • アクション: CI が決定的な理由で赤なら、1回修正を試みる。main が動いたら、1回 rebase する。
  • 予算: PR あたり修正1試行、5分、変更10ファイル。
  • 停止条件: CI 緑、または予算切れ。そこで止まって人間に ping。

壊れたビルドのバックログではなく、マージ済み PR に戻ってこられる。同じ形がほとんどの運用作業をカバーする:

  • CI ヘルス: 30分ごとに失敗 run を引き、signature でクラスタ化。1つの根本原因の赤10 PR が、見るべき1件になる。
  • デプロイ検証: push 後、エンドポイントを叩き、200 と期待される内容を確認、ユーザーより先にリグレッションを検出。
  • フィードバックのクラスタ化: 30分ごとにチャンネルのコメントを引き、テーマごとにグループ化、各クラスタを担当ファイル/ドキュメントに対応づける。

Claude Code の /goal を使った具体的ループ

子守は自分で配線するループ。エージェントに内蔵されたものも見ておくと役立つ。Claude Code では、最小の完全なループが /goal だ。検証可能な終了状態を渡すと、それが真になるまで turn を取り続ける。

/goal をセッション内コマンドとして使う例。セッションを立ち上げ、その中でゴールを設定する。

これは先ほどの「行動・チェック・繰り返し」と同じ形で、検証者が組み込まれている。

ここまでで明らかなのは、強い /goal はプロンプトというより契約のように読めること。良いものは4つを指定する: 欲しい終了状態、それに到達したと証明する証拠、エージェントが破ってはいけない制約、使ってよい作業の予算。どれか1つでも曖昧にすると、モデルは最も楽な解釈で隙間を埋める。早く止まる、近道する、あるいは成功を再定義して、トランスクリプトは完了に見えるのに実システムは壊れている、という具合に。

  • 条件を設定する。/goal + チェック可能な終了状態、例: /goal tests in test/auth pass。最初の turn が即座に始まる。
  • エージェントが1 turn 働く。編集し、テストを走らせ、結果をセッションに出す。
  • 評価者がチェックする。速いモデルがトランスクリプトを読み、満たされたか否かを判断する。エージェントが自分の仕事を採点しないように。
  • ループか終了か。未達なら指示付きでもう1 turn。達成ならゴールが自分でクリアし、run が止まる。

state は turn を跨いで運ばれるので、早く止めたり途中で制約を落としたりしない。信頼性を保つ制御がいくつかある:

  • チェックを測定可能に: テスト結果、exit code、ファイル数、空のキュー。npm test exits 0 はゴール、「もっと良くして」はゴールでない。
  • run を区切る: 「または20 turn 後に止まる」のように付け、詰まったループが turn を燃やし続ける代わりに停止するように。
  • auto モードと組む: turn が無人で走るように。早く中断するには /goal clear。

評価ステップには有用な機微が隠れている: チェッカーはコーダーと同じモデルである必要はない。ループが役割を分けたら（プランナー、実行者、評価者、ビジョンレビュアー）、各々を別のモデルで走らせられ、どの役割にどのモデルを当てるかが「1つの最良エージェントへの賭け」ではなく「アーキテクチャの決定」になる。あるモデルは計画が得意、あるモデルは安く実行、あるモデルはスクリーンショットの判定が正確。良いオーケストレーターは、1ベンダーが全カテゴリで勝つのを待つのではなく、役割ごとに入れ替えさせてくれる。

これは API 移行（全呼び出し箇所をコンパイル＆テスト通過まで移す）、リファクタ（各モジュールが予算未満になるまでファイルを分割）、issue バックログ（ラベル付きキューが空になるまで処理）、eval ループ（スコアが閾値を超えるまでプロンプトを調整）でうまく機能する。/loop は単一の終了線が無い作業の対応物で、完了条件の代わりにスケジュールで再プロンプトする。PR の子守のようなループはこれで走り続ける。

多数のループを無人で走らせる

単一の /goal ループは、1つの終了線へ向かう1エージェント。多数の無人プロセスを走らせると賭け金が上がる。ループは「自分の仕事をチェックできる能力」の分しか信頼できないからだ。Cherny の「Opus を数時間自律で走らせる」セットアップは5ステップに集約される:

  • 権限を自動承認し、エージェントがツール呼び出しごとに尋ねて止まらないように。
  • dynamic workflows を使う（プロンプトに Ultracode を入れる）。1本の直列スレッドではなく多数のエージェントに fan-out。
  • /goal か /loop で走らせ続ける。/goal は完了条件、/loop はスケジュール再プロンプト。両者とも state を運ぶので早く止まらない。
  • クラウドで走らせる（デスクトップ/モバイルアプリ）。ラップトップを閉じてもセッションが生き残る。
  • エンドツーエンドで自己検証する手段を与える。Web は Claude in Chrome、モバイルはシミュレータ MCP、バックエンドはライブサーバー。これが他の4つを安全にするステップ。

crabfleet: プロダクトとしての orchestration

orchestration は具体的なツールで描くと分かりやすい。Peter Steinberger の crabfleet（OpenClaw プロジェクトで「エージェント run の管制塔」と銘打つ）は、プロダクトとしてパッケージされたループで、その形は上記すべてに対応する。

  • ボード上のカードとしての作業: タスクはプロンプト・GitHub issue・PR から作るカードとして入力され、todo・running・human review・done を移動する。そのボードがループのキューであり、停止＆報告ステップを可視化したもの。
  • fire-and-forget ではない耐久 run: 各 run はハートビート付きの追跡された試行で、目を離しても走り続け、閉じたラップトップを生き延びる。ランタイムが handoff 対応を表明したときだけ引き継ぐ。
  • エージェントを spawn するエージェント: run は子セッションを起動し、メッセージを送り、トランスクリプトを読み、サンドボックス内から自分のサマリを更新できる。disk 上メモリと fan-out が一箇所に、1作者・多エージェント。

これは使い捨てのクラウドサンドボックス上でブラウザベースのターミナルで走る。それが無人 run から立ち去ることを安全にする。要点は特定のツールではなく、ループがインフラへと硬化したこと: キュー、耐久実行、fan-out、人間レビューのゲートが、毎回手で書くものではなく設定するものになった。

コストの所在が変わった

2年間、AIコーディングのコスト問題は単純だった。どのモデルで、何トークンか。ループの中では、その本能は間違った層を指す。支出はもはや単一の呼び出しではなく「ループが何周するか」だ。6回リトライして収束するループは、同じモデルで1回で着地するループの6倍かかる。

最適化すべきものが変わる:

  • 反復が予算項目で、トークンではない。2倍の頻度でループする安いモデルは安くない。track すべきは finished task あたりのコストで、呼び出しあたりではない。
  • 弱い検証者が出荷できる最も高コストなバグ。「done」を決めるチェックが緩いと、ループは壊れた仕事で早く止まるか、既に良かった仕事を延々と挽く。どちらも1反復まるごと無駄にする。何より先にこれを締める。
  • 早く失敗することはコスト管理。連続失敗に上限の無いループは、いずれ成功するのではなく、いずれ口座を空にする。停止条件はコードベースと同じくらい請求書を守る。

以前はプロンプトを調整した。今はループを調整する。コストはそこに溜まるからだ。

ループにすべきでない時

ループが効くのは、タスクが繰り返され、機械が「いつ終わったか」を判定できる時。それ以外では、ループは churn を自動化するだけ。次の場合は避ける:

  • 一発の編集: 1パスで終わるなら、ループは純粋なオーバーヘッド。
  • 未スコープ／探索的な作業: 「なぜユーザーが離脱するか探れ」には pass 条件が無く、ループは収束しない。
  • 安価な自動チェックが無いもの: 唯一の検証者が自分の目なら、まだループの中にいる。先にチェックを作るか、手でやれ。

何が起こりうるか

あなたが寝ている間に走るループは、寝ている間にミスもする。失敗モードは予測可能だ。

  • 検証負担は人間に残る: ループはあなたがレビューできるより速く書く。diff を読むのをやめれば、作業を除いたのではなく先送りしただけ。
  • 理解のギャップが広がる: 自分が書いていないコードを、吸収できるより速く出荷すると、自分のシステムのモデルが侵食され、その負債は次のインシデントで返済を迫る。
  • 緩いチェックでの静かなドリフト: 弱い検証者は「間違っているが通る」仕事を毎反復通す。ループは生産的に見えながら穴を掘る。

これらはループへの反論ではない。だからこそ「ループを設計するエンジニア」がより重要になる、ということだ。

自分のループの作り方

  • 繰り返せるタスクを1つ選ぶ: PR の子守、CI 修正、デプロイ検証。ルーチン作業から始める。
  • タイトにスコープする: 「billing webhook の検証を直す、触るのは app/api/billing と lib/billing だけ」は「バグを直す」に勝る。緩いループはさまよう。
  • 予算と停止条件を与える: 最大試行、最大実行時間、最大ファイル、最大支出、最大連続失敗。無人で走るループは、無人でミスをするループでもある。
  • 独立した検証者を加える: 別のサブエージェントが採点する。コードを書いたエージェントは「終わったか」の最悪の判定者。
  • カデンスで走らせる: 間隔なら /loop、スケジュールなら cron、ライフサイクル地点なら hooks、閉じたラップトップを生き延びさせるなら GitHub Actions。
  • メモリを disk に保つ: モデルは実行間で忘れるので、state は context window ではなく Markdown かボードに。

要点: いまや高コストで失敗しやすいのは、モデルではなくループだ。「run を始める人」ではなく「出力に責任を持つエンジニアであり続けるつもりの人」のように、ループを作れ。
