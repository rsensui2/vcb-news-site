Fable に「実装指示書」を書かせ、Codex/Opus で実装する — /goal ワークフロー用プロンプト

概要

Fable ボーナス期間中の使い分けとして、Fable には実装そのものより「コードベースを深く読ませて、Codex や Opus 等の実装担当モデルに渡す指示書を作らせる」方が相性が良い、という運用知見。投稿者はさらに、実装モデル側が /goal コマンドで走らせる前提の指示書（refactor-instructions.md）を Fable に生成させるためのプロンプトを公開した。

まとめ

  • 役割分担: Fable = プロジェクト全体を読み込み、仕様・技術的負債・危険箇所を整理して Markdown 指示書を書く「分析担当」。Fable 自身は実装しない。
  • 実装担当（Codex/Opus）へは /goal refactor-instructions.md に書かれたことを完遂しろ の形で渡す。
  • 指示書に必ず含める章立て: Objective / Project Understanding / Behaviors To Preserve / Non-Negotiables / Stop And Ask Conditions / Baseline Commands / Debt Map / Implementation Phases / Verification Requirements / Reporting Format / Out-of-scope Items。
  • 実装フェーズは「小さく安全な順」に固定: ①現状と検証コマンド確認 → ②重要挙動に安全網（テスト/再現手順）→ ③明らかに安全な整理 → ④小さな責務分離 → ⑤境界・IF明確化 → ⑥テストしやすい構造 → ⑦大きな設計変更は承認なしに実装せず提案に留める。
  • ガードレール: 最初に git status、未コミット変更と自分の変更を混ぜない、baseline 検証結果を記録、無関係な整形をしない、正しさが不明なら止めて質問。
  • 「全部リファクタして」的な曖昧計画・見た目の綺麗さ目的・古いコードを一律に悪と決めつける、を明確に禁止。
