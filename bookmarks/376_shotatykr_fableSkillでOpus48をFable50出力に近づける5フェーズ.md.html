/fable Skill を自作 — Opus 4.8 を Fable 5.0 の出力に近づける5フェーズ

概要

Fable 5.0 が有料プランから外れるなら、/fable という Skill を作って Opus 4.8 で Fable 5.0 の出力に近づければいい、という発想で実際に作ってみた投稿。Fable が難しいタスクを解くときに辿っているらしい5フェーズ（Phase 0〜4）を言語化し、冒頭で3つの原則を刷り込む構成。前掲 @0x_kaize の「Fable に SKILL.md を書かせる」提案を、具体的なフェーズ設計として肉付けした実例になっている。

まとめ

  • 冒頭の3原則:

- 完了条件を先に固定する — 検証方法が書けないタスクは、まだ理解できていないとみなす

- 自分の主張ではなく観測を信じる — 「動くはず」は証拠ではない。実物を見るまで完了と言わない

- 次の一手は「いま一番リスクが高い場所」で選ぶ — 元の計画の次の行ではなく

  • Phase 0（3行を書く）: 「完了条件（観測可能な形で）／検証方法（コマンド・diff・実行結果）／やらないこと」。この3行が錨。検証方法の行が書けないなら理解不足なので先に調べに行く。
  • Phase 1（偵察）: 計画の前に実物を軽く読み、「事実／仮定／不明」の3つに仕分ける。核心は「一番危険なのは事実のふりをした仮定」。
  • Phase 2（分解）: 概念ではなく「独立して検証できる単位」で切る。順序はリスク順で、外れたら計画が崩れる仮定の検証を最初に。「簡単なところから片付けて勢いをつけるのは罠」。
  • Phase 3（実行ループ）: 1ピースずつ進めてその場で検証（最後にまとめて検証しない）。毎回4つの自問で次の一手を選び直す —「観測は計画と矛盾していないか／いま最大のリスクはどこか／次の行動は可逆か／人間にしか答えられないことで詰まっているか」。行動と調査の使い分けは「手戻りコストと確認コストの比較」で決める。
  • Phase 4（全体検証）: v2で研いだ心臓部。①作った層と別の層で確認する（コードなら実行、文章なら初見の読者として読む）②壊しに行く（空入力・境界値を実際に当てる）③原因の説明を観測で裏取りする（各原因に証拠を1つずつ、なければ「寄与は未確認」と書く）④依頼原文との突き合わせ⑤diff通読。
