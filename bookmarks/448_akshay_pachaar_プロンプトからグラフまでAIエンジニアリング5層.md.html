投稿本文（日本語訳）

prompt → context → harness → loop → graph engineering。

用語リストは増え続け、新しい語が出るたびに前の語を「置き換えるもの」として扱われる。だが実際には各層が前の層を包み込んでいる。見分ける一番きれいな方法は、「1 単位の作業とは何か」を問うことだ。

プロンプトエンジニアリングは「メッセージ」である。

モデルはこの呼び出し以前を何ひとつ覚えていない。だからプロンプトが、必要な世界のすべてを運ばなければならない。役割、背景、指示、いくつかの例、フォーマット。

出力が期待に届かなかったとき求められる技術は、毎回指示を書き直すことではなく、どの材料が足を引っ張ったのかを突き止めることだ。

作業の単位は「1 つの入力」。

コンテキストエンジニアリングは「メモリ」である。

多数のステップにまたがると、ウィンドウは有限で、使える情報は無限。そこでキュレーションの工程が強制的に要る。キュレーターは、重要なものを残し、有用だが嵩張るものを圧縮し、残りを捨てる。

良いキュレーションとは、より多く詰め込むことではなく、ほとんどが何を捨てるかを知っていることだ。

作業の単位は「ウィンドウに残ったもの」。

ハーネスエンジニアリングは「機械」である。

モデル単体は、ただテキストを生成するだけ。ハーネスは必要なものを集め、実行し、ツールやサブエージェントを呼び、テストや judge で結果を検証する。

この検証ステップこそが、「API を呼ぶ」ことと「エージェントを走らせる」ことの差分のすべてだ。

作業の単位は「機械を 1 回通すこと」。

ループエンジニアリングは「ラン」である。

1 回のパスで仕事が片付くことは稀だ。だから「機械をもう一度回すか」を決める何かが要る。その判断には、事前に定義されたゴール、最大反復回数や予算上限といったブレーキ、そして体感ではなく自動化された完了判定が必要になる。

ツールを要求しなくなったエージェントは、自分のターンを終えただけであって、タスクを終えたわけではない。

作業の単位は「ラン全体」。

図はここまでの 4 つを扱っている。5 つ目はこれだ。

グラフエンジニアリングは「協調」である。

複数のループが協働しなければならなくなると、何がいつ走るのか、何が並列なのか、誰が誰をチェックするのかを宣言する必要が出てくる。ノードが作業をし、エッジが次に何を走らせるかを決め、共有状態がその間を流れる。

単一のループとは、自分自身を指すエッジを 1 本持った 1 ノードのグラフにすぎない。だからこそグラフはループを置き換えるのではなく、ループを統べる。

作業の単位は「ジョブ全体」。

そして、これらを結びつけるのが次の部分だ。

プロンプトとコンテキストは、どちらもハーネスの「集める」ステップの中に住んでいる。ハーネスは 1 パス、ループはそのパスをもう一度走らせるかを決め、グラフはそもそもどのループを走らせるかを決める。

ズームアウトすれば作業の単位は大きくなる。ズームインすれば、また元のプロンプトに戻ってくる。

これはデバッグ場所の指針にもなる。作業の単位が壊れた層を見つけ、その層を直せ。

プロンプトは最も編集しやすい層だ。だからこそ、3 層上で起きた失敗の責任まで押し付けられ続けている。

私はグラフエンジニアリングについての深掘り記事も公開した。中核となる考え方、始め方、共有状態、信頼できるルーティング、そしてグラフが本当にオーバーキルになるのはどんなときか、を扱っている。記事は引用ポストにある。

<summary>原文 (English)</summary>

from prompt → context → harness → loop → graph engineering.

the list keeps growing, and every new term gets treated as a replacement for the last one. each layer wraps the one before it, and the cleanest way to tell them apart is to ask what a single unit of work looks like.

prompt engineering is the message.

the model remembers nothing before this call, so the prompt has to carry the full universe of what it needs. a role, the background, the instructions, a few examples, a format.

when the output falls short, the skill is working out which ingredient let you down, not rewriting the instructions every time.

the unit of work is one input.

context engineering is the memory.

across many steps the window is finite and the available information is not, which forces a curation step. a curator keeps what matters, compresses what is useful but bulky, and drops the rest.

good curation is mostly about knowing what to throw away, not packing more in.

the unit of work is what stays in the window.

harness engineering is the machine.

on its own a model just generates text. the harness gathers what it needs, runs it, calls tools or sub-agents, and verifies the result with tests or a judge.

that verify step is the entire difference between calling an api and running an agent.

the unit of work is one pass through the machine.

loop engineering is the run.

one pass rarely finishes the job, so something has to decide whether to run the machine again. that decision needs a goal defined upfront, brakes like max iterations and budget caps, and a completion check that is automated rather than felt.

an agent that stops asking for tools has ended its turn, which is not the same as finishing the task.

the unit of work is the whole run.

the diagram covers those four. here is the fifth.

graph engineering is the coordination.

once several loops have to work together, you need to say what runs when, what runs in parallel, and who checks whom. nodes do the work, edges decide what runs next, and shared state flows between them.

a single loop is just a one-node graph with an edge pointing back at itself, which is why graphs govern loops instead of replacing them.

the unit of work is the whole job.

here is the part that ties it together.

prompt and context both live inside the harness gather step. the harness is one pass, the loop decides whether to run that pass again, and the graph decides which loops run at all.

zoom out and the unit of work gets bigger. zoom in and you are back at the prompt.

that also tells you where to debug. find the layer whose unit of work broke, then fix that layer.

the prompt is the easiest layer to edit, which is why it keeps taking the blame for failures that live three layers up.

</details>

概要

「プロンプトエンジニアリング」「コンテキストエンジニアリング」「ハーネスエンジニアリング」「ループエンジニアリング」、そして新しく「グラフエンジニアリング」——次々に増えるこれらの用語は、互いを置き換える競合概念として語られがちだが、実際は入れ子構造であり、見分ける唯一クリーンな基準は「1 単位の作業 (a single unit of work) が何か」だと整理した投稿。5 層それぞれの unit of work を定義し、デバッグすべきレイヤーの特定法まで一本の論理でつないでいる。

まとめ

  • prompt = メッセージ。モデルはこの呼び出し以前を何も覚えていないので、必要な世界のすべて（役割・背景・指示・例・フォーマット）をプロンプトが運ぶ。出力が悪いとき求められるスキルは「毎回指示を書き直すこと」ではなく「どの材料が足を引っ張ったかを特定すること」。unit of work = 1 入力
  • context = メモリ。複数ステップにまたがると、ウィンドウは有限で情報は無限なのでキュレーションが強制される。良いキュレーションは「詰め込む」ことではなく何を捨てるかを知っていることが本質。unit of work = ウィンドウに残ったもの
  • harness = 機械。モデル単体はテキストを生成するだけ。ハーネスが必要なものを集め、実行し、ツールやサブエージェントを呼び、テストや judge で結果を検証する。この verify ステップこそが「API を叩く」と「エージェントを走らせる」の全差分
  • loop = ラン。1 パスで仕事が終わることは稀なので、「機械をもう一度回すか」を決める何かが要る。その判断には ①事前に定義したゴール ②最大反復回数・予算上限といったブレーキ ③体感ではなく自動化された完了判定 が必要。ツールを要求しなくなったエージェントはターンを終えただけで、タスクを終えたわけではない。unit of work = ラン全体
  • graph = 協調。複数のループが協働し始めると、何がいつ走り、何が並列で、誰が誰をチェックするかを宣言する必要がある。ノードが作業し、エッジが次を決め、共有状態がその間を流れる。単一ループは「自分に戻るエッジを1本持つ1ノードのグラフ」にすぎず、だからグラフはループを置き換えるのではなく統べる
  • 層の入れ子関係: prompt と context はどちらもハーネスの gather ステップの中に住む。ハーネスは 1 パス、ループはそのパスを再実行するか決め、グラフはそもそもどのループを走らせるか決める。ズームアウトすると unit of work が大きくなり、ズームインすればプロンプトに戻る
  • デバッグの指針: unit of work が壊れたレイヤーを見つけて、そのレイヤーを直す。プロンプトは最も編集しやすい層なので、3 層上で起きた失敗の責任まで押し付けられ続けている
  • 著者は引用ポストでグラフエンジニアリングの深掘り記事（コア概念・始め方・共有状態・信頼できるルーティング・グラフが明確にオーバーキルになる条件）を公開している
