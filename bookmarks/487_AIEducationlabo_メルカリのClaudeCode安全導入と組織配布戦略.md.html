メルカリのClaude Code安全導入と組織配布戦略

AIコンサルの現場で、経営者からよく聞かれる質問があります。

「Claude Codeのセキュリティ、結局どうすればいいですか?」

こちらに対しては、メルカリ社が、2026年4月10日、メルカリ本社(六本木ヒルズ森タワー26階)で開かれた「Claude Code Meetup Japan #4」というエンジニア向けの勉強会での「Claude Codeセキュリティ設定の組織配布戦略」という発表資料が非常に参考になります。

この発表資料は、個人のAIコンサルタントが「経営者・情シス・PM全員が読むべき内容」と紹介し、金融業界でAI推進をしている書き手が「これをベースに、銀行だったら何を足すか」を考察し、他にも複数のブログが同じスライドを題材に記事を書いています。1社の社内発表が、これだけ広く参照されるのは珍しいことだと思います。

そこで今回は、この発表そのものの中身に加えて、「なぜこの話がここまで広がったのか」「発表のあとに何が起きているのか」まで、僕なりに調べて整理してみました。単に設定をコピペするだけでなく、その裏側まで理解しておくと、自社に応用するときの判断がしやすくなるはずです。

そもそも、なぜ今このテーマが刺さるのか

背景には、AIの性質そのものの変化があります。これまでのChatGPTのようなAIは、人が質問して、AIが答えるだけの「対話型」でした。一方Claude Codeは、AI自身がファイルを読み書きし、コマンドを実行し、ネットにも取りに行く「自律型(エージェント型)」です。

この違いは大きいです。対話型のAIなら、変な回答をされても実害はコピペする前に人間が止められます。でも自律型のAIは、AI自身がもう手を動かしてしまっているので、気づいたときには何かが実行された後、ということが起こり得ます。

Claude Codeの利用が非エンジニアにも広がり始めた今、多くの経営者が「便利なのは分かるけど、何がどこまで起こり得るのか分からない」という状態で足踏みしています。メルカリの発表は、この漠然とした不安に、実際の設定という具体的な答えを出した。だからこそ刺さったのだと思います。

何が「怖い」のか、具体的な話をします

メルカリの発表では、想定すべき最悪のシナリオとして「誤ったrm -rf(削除コマンド)の実行」と「curl(外部通信コマンド)経由の情報漏洩」の2つが挙げられていました。抽象的な話に聞こえるかもしれませんが、これは決して大げさな心配ではありません。

2026年に入ってから、Claude Code自体にも実際の脆弱性が報告されています。セキュリティ専門機関のCheck Point Researchが公表した脆弱性のひとつでは、悪意のある第三者が用意したリポジトリ(コードの保管場所)を開くだけで、確認画面が出る前に不正なコードが実行されてしまう問題が指摘されました。また別の脆弱性では、接続先の設定を書き換えることで、認証情報が外部のサーバーに送られてしまう経路も見つかっています。いずれもClaude Code側で修正版が配布されていますが、「知らない相手が作ったフォルダを、何の確認もなく開く」という何気ない行動が、事故の入り口になり得ることが分かります。

ちなみに、こうした攻撃への防御は現状まだ発展途上です。AIエージェントに対する巧妙な"命令の混ぜ込み"(プロンプトインジェクション)は、最先端の防御を持ってしても防ぎきれないケースが多いと報告する研究もあります。この手の数字は書き手によってばらつきがあり、僕自身も一次の論文までは確認しきれていないので、正確な数値として鵜呑みにはしていません。ただ、「AIが自力で悪意ある指示を見抜いてくれる」という期待は、今の時点では持たないほうがいい、という方向性は複数の情報源で一致しています。

メルカリが実際にやったこと

発表の中身自体は、意外とシンプルです。要点だけ振り返ります。

確認を全部スキップする危険なモードを、管理者設定で使えなくする

curlやwgetのような外部通信系のコマンドは拒否リストに入れるか、実行前に必ず確認させる

.envファイルやSSHキーなど、秘密情報が入ったファイルは読み取り自体を禁止する

sandbox機能で、作業フォルダの外や許可していないネット先には物理的に触れられなくする

CLAUDE.mdという指示書ファイルに、会社としてのセキュリティ方針を書いておき、AIに毎回読ませる

ここまでは「よくできた設定集」の話です。でも、他の書き手の分析を読んでいて、僕がなるほどと思ったのは、この設定の中身そのものより「誰にどう配るか」という設計のほうにあります。

本当に効いていたのは、設定の中身より「配り方」

メルカリは、この設定をMDM(会社が社員のパソコンを一括管理する仕組み。メルカリではJamfというツールを使っています)経由で全社員に配っています。ポイントは、配る内容を一律にしなかったことです。

エンジニアには、安全性を保ちつつ、ある程度カスタマイズできる設定

エンジニア以外の社員には、いじる余地をほぼ残さない、いちばん厳しい設定

同じClaude Codeというツールでも、使う人によって必要な自由度がまったく違います。エンジニアにとっては「安全を保ちながら生産性を落とさないこと」が大事ですが、非エンジニアにとっては「そもそも触って壊れないこと」のほうが大事です。この2つを1つの設定で両立させようとすると、たいてい中途半端になります。属性ごとに違う「安全な初期値」を配る、という発想の転換が、この発表がただの設定集で終わらなかった理由だと思います。

これは実は、Claude Codeに限った話ではありません。今後、CodexやCursor、他のAIエージェントを会社に入れるたびに、同じ論点が繰り返し出てくるはずです。AI導入の競争は、そのうち「どのAIが賢いか」ではなく「どう安全に統治するか」に軸足が移っていく。そんな予感がします。

この発表は、あくまで入り口

もうひとつ紹介したいのが、この発表をベースに、金融業界向けの設計を独自に考察していたエンジニアのブログです。金融機関でAI推進をしているという書き手が、「メルカリの発表は端末・設定レベルとしては十分。ただ金融機関では、その上にさらに3つの層を積み上げる必要がある」という整理をしていました。

端末・設定層: メルカリの発表がカバーしている範囲(MDMでの設定配布など)

インフラ・契約層: どの経路でAIに接続するか(例えば海外のサーバーを直接使わず、国内リージョンを経由する構成にするなど)

監査・コンプライアンス層: 誰が・いつ・何をAIに入力したかを、何年分残しておくか

ガバナンス層: 経営レベルでの承認体制や、規制当局への説明責任

金融機関ほど厳格な業界の話ではありますが、この「層で考える」という視点自体は、規模の大きくない会社にも役立ちます。今日やるべきなのは一番下の層(設定を配ること)で十分ですが、「その上にはこういう層がある」と知っておくだけで、事業が大きくなったときや、扱うデータの機密性が上がったときに、何を足せばいいか判断しやすくなります。

中小企業なら、ここから始める

最小セットは、こちらです。

{ "permissions": { "disableBypassPermissionsMode": "disable", "deny": [ "Bash(curl:)", "Bash(wget:)", "Bash(sudo:)", "Read(.env)", "Read(.env.)", "Read(/.ssh/)" ], "ask": [ "Bash(git push:)", "Bash(rm:)" ] } }

これを.claude/settings.jsonという名前で保存し、Claude Codeを使うフォルダの直下に置くだけで動きます。会社全体に強制したいなら、ホームフォルダ直下の~/.claude/settings.jsonに置いてください。

そのうえで、社員が複数いるなら、いきなり全員に同じ設定を配るのではなく、「エンジニア(または業務でコードを触る人)」と「それ以外」で、渡す設定の厳しさを変えることをおすすめします。難しく考える必要はなく、非エンジニア向けには上のdenyリストをさらに厚くする、くらいの調整で十分です。

落とし穴: この手の"教科書"を真似るときに気をつけたいこと

ネットに出回っている設定のコピペをそのまま信じない。今回いろいろな記事を読み比べていて気づいたのですが、同じ「確認スキップを禁止する設定」でも、記事によってキー名の書き方が微妙に違いました。僕が確認した限り、Anthropic公式ドキュメントに載っているのはdisableBypassPermissionsModeという名前です。人づてに広がるうちに、正確な情報が少しずつ崩れていくことがあるので、最終的には必ず公式ドキュメントで裏を取ることをおすすめします。

「メルカリがやっているから安全」で思考停止しない。メルカリの設定は、あくまでメルカリの事業内容・扱うデータ・組織規模を前提にした設計です。自社が扱う情報の機密性や、業界の規制によっては、もっと厳しい設定や、逆にもっと緩い運用でも十分な場合があります。

設定を配って終わりにしない。設定という「物理的な鍵」と、判断力を育てる「教育」は両輪です。どちらか一方だけでは、いずれどこかで隙ができます。

中級者向けFAQ

Q. こういう発表がバズると、内容の信頼性はどう見分ければいいですか?

発表そのものが一次情報で、そのあとに出てくる解説記事はすべて二次情報だと考えるようにしています。二次情報は分かりやすく整理されている分、細かい部分で表記のズレや、書き手の解釈が混ざっていることがあります。気に入った記事があっても、実際に設定を使う前には、必ず一次情報(この場合はAnthropicの公式ドキュメントと、元のSpeaker Deck)まで戻って確認するのが安全です。

Q. 中小企業がここまで厳格にする必要は本当にありますか?

守るべき情報の中身次第です。顧客の個人情報や、外に出たら困る契約情報を扱っているなら、規模に関係なくやっておいたほうがいいです。逆に、社外秘の情報をほとんど扱わない業務であれば、最初は.envの読み取り禁止だけでも十分だと思います。完璧を最初から目指さず、扱っている情報の重さに応じて調整するのが現実的です。

Q. こうした発表を追いかけること自体に意味はありますか?

あると思います。1社の発表がここまで広く参照されるということは、それだけ多くの会社が同じ悩みを抱えているということです。自社だけで手探りするより、すでに複数の会社が検証した設計を土台にして、自社に合わせて調整するほうが、確実に早いです。

まとめ: 教科書は、そのまま写すものではなく、土台にするもの

メルカリの発表が広く参照されるようになった理由は、設定の中身がよくできていたことに加えて、「誰にどう配るか」という、AI導入における普遍的な課題にきちんと答えていたからだと思います。

なぜ怖いか: AIが自律的にファイルを操作し、コマンドを実行するようになったことで、実際の脆弱性を突かれる事故が起こり得る

メルカリの答え: 危険な操作を設定でブロックし、属性(エンジニアかどうか)に応じて配る内容を変える

この先: メルカリの発表はあくまで入り口。業界や扱う情報によって、インフラ・監査・ガバナンスといった上の層を自社で足していく必要がある

最後に、今日からの3ステップです。

一次情報を確認する: 気に入った解説記事があっても、最後は公式ドキュメントで設定のキー名を確認する

最小セットを配る: 上のpermissionsの例を、まず自分のパソコンに入れてみる

配る相手で内容を変える: 社員が複数いるなら、コードを触る人とそれ以外で、渡す設定の厳しさを分ける

AIを安全に使えるようにすることは、それ自体が目的ではありません。設定を整えるのは、社員が安心してAIを使いこなし、実際の成果につなげるための土台づくりです。教科書はそのまま丸写しするものではなく、自社の状況に合わせて調整して初めて意味を持ちます。

AIを「知っている」から、「仕事で使える」へ

私は現在、企業や事業者の方/個人事業主の方に向けて、AI導入・業務効率化・AIを活用した事業づくりの支援を行っています。

この記事を読んで、

AIを仕事に取り入れたいが、何から始めればよいか分からない

ChatGPTは使っているが、業務効率化や売上向上につながっていない

自社に合ったAI活用の方法を整理したい

AIを活用した新規事業や業務改善を進めたい

と感じた方もいるかもしれません。

AIツールを紹介するだけではなく、現在の業務や課題を整理したうえで、

「どの業務に、どのようにAIを組み込み、実際の成果につなげるか」

まで一緒に考えることを大切にしています。

Summary

メルカリの「Claude Codeセキュリティ設定の組織配布戦略」を起点に、エージェント型AIを企業で安全に導入するための設定・配布・ガバナンスを整理した長文解説。危険な権限バイパスの禁止、外部通信コマンドや機密ファイルへのアクセス制限、sandbox、CLAUDE.mdでの方針明文化に加え、エンジニアと非エンジニアで安全な初期値を分け、MDMで組織配布することが中核だとしている。

Key points

  • エージェント型AIはファイル操作・コマンド実行・外部通信まで行うため、対話型AIとは異なる実害リスクがある
  • disableBypassPermissionsMode、危険コマンドの deny/ask、.env や SSH キーの Read 禁止が最小防御になる
  • sandboxで作業ディレクトリ外や未許可ネットワークへのアクセスを物理的に制限する
  • 統一設定ではなく、エンジニアには生産性との両立、非エンジニアには変更余地を減らした厳格設定を配る
  • MDMによる組織配布で、個人の善意や設定漏れに依存しない運用にする
  • 高規制業界では端末設定に加え、インフラ・契約、監査・コンプライアンス、経営ガバナンスの層を追加する
  • 二次解説の設定例をそのまま信じず、Anthropic公式ドキュメントと元発表でキー名・挙動を確認する

Takeaway

企業のAI導入は「便利なツールを配る」だけでは成立しない。役割別の安全な初期値、強制配布、監査可能性、継続教育までを一つの運用設計として持つことで、利用者の判断力に依存せず安全性と生産性を両立できる。
