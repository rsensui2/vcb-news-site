natural-japanese スキルを更新しました。

https://artifactshare.com/a/2aretj5195

記事本文

何が変わったか

natural-japanese の v1.4.0 で、新しいレーンを追加しました。目的は「AI臭さの検出」とは別です。読解負荷を指し示すためのもので、lint.py --reading-load というオプトインのフラグとして実装しています。既存の出力への影響は一切ありません。あわせて、悪文パターンを集めたカタログを読解負荷の大きい順に並べ替え、既存の検出器に含まれていた誤検知も修正しました。

きっかけ

きっかけは meiseki でした。日本語の明晰化だけを扱う、別のプラグインです。meiseki は、textlint による決定論的な検出層と LLM による文脈判断層を組み合わせている点で、natural-japanese と近い設計思想を持ちます。この二層構成自体はすでにある発想でしたが、読解負荷の高い順に A から H までカタログを並べる構成には、参考にできる点がありました。

そこで、natural-japanese が「機械的な閾値化ができない」と結論づけていた読みやすさの領域について、もう一度検討することになりました。

なぜ一度は「検出できない」と結論づけていたのか

natural-japanese には corpus/reports/readability-sweep.md という検証レポートがあり、そこでは文長・読点密度・二重否定・漢字比率などの14の候補について、コーパスを使った検証が行われていました。結果は実装推奨0件でした。「読みやすさは判断領域であり、機械的な閾値化はできない」という結論です。

この結論を踏まえると、読解負荷を検出する新しい機能を追加することは、一度否定された道を再び歩くことになります。実際、この検証の存在を知らずに同じ検出器を提案し、既存のレポートによって指摘され、撤回するという経緯もありました。

しかし、この NO-GO 判定の意味を改めて確認すると、判定基準は「AIが書いた文章か人間が書いた文章かを見分けられるか」という弁別力にありました。たとえば文長についての判定は、AI検出率が1.0%であることを理由にNO-GOとされていました。しかしこれは「長い文章はAIが書いた証拠にはならない」という意味であって、「長い文章は読みやすい」という意味ではありません。

読解負荷レーンが解決したい課題は分類ではなく推敲です。目的が違えば、採用する基準も違ってよいはずだと考え、「その指摘に従って文章を直したとき、実際に読みやすくなるかどうか」という基準で、改めて検出器を作ることにしました。

実装した検出器

最終的に実装した検出器は5つです。

  • sentence_too_long — 一文が長すぎる文を指す
  • buried_list — 同格の項目が埋もれた列挙を指す
  • double_negative — 二重否定になっている箇所を指す
  • kanji_run — 漢字が連続しすぎている箇所を指す
  • no_chain — 格助詞の「の」が連鎖している箇所を指す

いずれも severity は info のみで、判定やスコアは一切出しません。あくまで「ここを見てください」という指し示しに徹しています。

既存の自然度スコアや --baseline による差分比較には、この読解負荷レーンの結果を一切混ぜていません。これは意図的な設計判断です。AI臭さの採点という目的と、読みやすさの推敲という目的を同じスコアに混ぜてしまうと、どちらの判断も曖昧になってしまいます。--reading-load フラグを付けない限り、v1.4.0以前の出力はまったく変わりません。

検出器を追加してよい基準

142字ある一文は、実際に読めば長いとわかります。AIであっても、それを読み流せば長さに気づくはずです。それでも検出器は必要です。理由は網羅性にあります。15,000字規模の文章を読んでいるとき、11本ある長い文のうち何本かには気づいても、全部には気づきません。機械であれば、それを漏れなく拾えます。

したがって、この読解負荷レーンに検出器を追加してよいのは「読み流すと見落としてしまうもの」に限られます。読めば確実に気づくものにまで検出器を追加しても、指摘の件数が増えるだけで、判断の質は上がりません。

この基準に基づいて、当初実装していた「接続助詞の『が』が連鎖している箇所を指す検出器」は削除しました。実際のデータで確認したところ、AIが生成した9,889文の中でこの検出器が反応したのは1件だけで、人間が書いた379文では0件でした。

コーパスでの校正

読解負荷レーンの各検出器は、実際の文書241本、合計9,889文のコーパスを使って校正しました。このコーパスはAIが生成した文書がほとんどを占めています。

校正の過程では、当初実装していた「読点が一文に4個以上ある箇所を指す検出器」を廃止することになりました。この検出器は文書の62%で反応してしまい、中身を確認すると、そのほとんどが同格の項目を並べた列挙でした。つまり問題は読点の打ち方ではなかった。列挙が一文の中に埋もれてしまっていることだったのです。そこで検出器そのものを作り直し、列挙を指す buried_list として実装しなおしました。

漢字が連続する箇所を指す検出器についても、当初は「東京地方裁判所」のような固有名詞まで拾ってしまう問題がありました。固有名詞は分解できない名前であり、書き手が直せる読みにくさではありません。形態素解析の結果を使って固有名詞を除外することで、この誤検知を取り除きました。

人間が書いた文章での検証

2024年に公開された技術記事10本、合計379文を人間執筆側のサンプルとして追加で検証しました。結果、AI生成コーパスでは1,000文あたり145件の指摘が出るのに対し、人間執筆のコーパスでは1,000文あたり37件と、約4倍の開きがありました。少なくとも、人間の良い文章に対してこのレーンが過剰に反応することはないと確認できたことになります。

ただし、この差を書き手の違いだけで説明しきれません。文書の種類自体が異なります（短い技術チュートリアルと、内容の詰まった仕様書や分析メモ）。実際、同じ書き手による記事でも、長文の分析記事が増えた年には指摘密度が1,000文あたり62件まで上昇していました。このレーンが測っているのは「AIらしさ」や「文章の下手さ」ではないようです。近いのは、一文あたりにどれだけ内容が詰め込まれているかという密度です。

カタログの再構成

悪文パターンをまとめたカタログの再構成も行いました。従来は文・語彙・段落・表記という4つの層で整理されていましたが、これを読解負荷の大きさの順に並べた A から J までの27項目に組み替えました。

大きく変えたのは各項目の「検出」欄の書き方です。これまでは「未実装」「目視確認」とだけ書かれていましたが、コーパス検証で得られた具体的な数値に置き換えました。「未実装」とだけ書かれていると、同じ検出器の追加が繰り返し提案され、そのたびにコーパス検証をやり直すことになります。

見つかったバグ

既存の検出器に含まれていたバグも見つかりました。原因は記号でした。文頭の反復を検出する機能が、Markdown の強調記法（強調）や画像記法（![alt](url)）のマーカーを、文頭の2形態素として数えていたのです。

実際の技術記事60本で確認したところ、この検出器が出した指摘のうち42%が、この記号によるものでした。日本語の形態素解析器 sudachi では、これらの記号がすべて「補助記号」として切り出されるため、品詞情報を使ってこれらを除外するよう修正しました。

まとめ（原文）

v1.4.0でもっとも大きい変更は、読解負荷という新しい軸を、AI臭さの検出とは明確に切り分けたレーンとして追加したことです。一度は機械的な検出ができないと結論づけた領域でした。しかし、その結論が前提としていた基準（弁別力）と、今回必要としていた基準（推敲後の読みやすさ）が異なっていたことに気づき、実装に至りました。

まとめ

日本語文章 lint スキル natural-japanese が v1.4.0 で「読解負荷レーン」を追加した。lint.py --reading-load のオプトインフラグで、sentence_too_long / buried_list / double_negative / kanji_run / no_chain の5検出器が severity=info の指摘だけを返す。既存の「AI臭さ」スコアには一切混ぜない設計。過去に「読みやすさは機械的に閾値化できない」と NO-GO 判定した領域だが、その判定基準が「AIか人間かの弁別力」だったのに対し、今回は「直したら読みやすくなるか」という推敲基準で検討し直して実装に至った。
