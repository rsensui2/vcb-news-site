Title: Karpathy's 4 CLAUDE.md rules cut Claude mistakes from 41% to 11%. After 30 codebases, I added 8 more In late January 2026, Andrej Karpathy posted a thread complaining about how Claude writes code. Three failure modes: silent wrong assumptions, over-complication, orthogonal damage to code it shouldn't have touched. Forrest Chang read the thread, packaged the complaints into 4 behavioral rules in a single CLAUDE.md file, and dropped it on GitHub. It hit 5,828 stars in the first day. 60,000 bookmarks in two weeks. 120,000 stars today. The fastest-growing single-file repo of 2026. Then I tested it on 30 codebases over 6 weeks. The 4 rules work. Mistakes that used to happen ~40% of the time dropped to under 3% on tasks that played to their strengths. But the template was built to fix code-writing mistakes from January. The Claude Code ecosystem in May 2026 has different problems — agent fights, hook cascades, skill loading conflicts, multi-step workflows that break across sessions. So I added 8 more rules. The original 4 rules (Forrest Chang / Karpathy) 1. Think Before Coding — No silent assumptions. State what you're assuming. Surface tradeoffs. 2. Simplicity First — Minimum code that solves the problem. No speculative features. 3. Surgical Changes — Touch only what you must. Don't refactor what isn't broken. 4. Goal-Driven Execution — Define success criteria. Loop until verified. These 4 close ~40% of failure modes in unsupervised Claude Code sessions. The 8 new rules 5. Don't make the model do non-language work — Retry logic, routing, escalation should be deterministic code, not LLM decisions. 6. Hard token budgets, no exceptions — Without budgets, every loop can spiral into 50,000-token context dumps. 7. Surface conflicts, don't average them — When patterns disagree, Claude tries to please both. Result: doubled error handlers, swallowed errors. 8. Read before you write — Surgical Changes tells Claude not to touch adjacent code; doesn't tell Claude to understand it first. 9. Tests are not optional, but they're not the goal — "Tests pass" becomes the only goal; shallow tests pass while everything else breaks. 10. Long-running operations need checkpoints — Without them, one wrong turn at step 4 cascades into broken steps 5 & 6. 11. Convention beats novelty — Introducing a second pattern is worse than either pattern alone. 12. Fail visibly, not silently — Most expensive failures look like success (migration "completes" but skips 14% of records). 仕様・計画・探索 — Markdown のプラン 1 枚ではなく HTML ファイルの「網」を作る。ブレスト、モックアップ、コードスニペット、実装プランを順に積み、満足したら新セッションでまとめて実装させる。検証エージェントにも同じファイル群を渡せる。 - コードレビュー・コード理解 — diff、注釈、フローチャート、モジュール図を埋め込める。GitHub のデフォルト diff より分かりやすい。すべての PR に「HTML コード説明書」を添付している。 - デザイン・プロトタイプ — Claude Design は HTML ベース。React や Swift が最終形でも、まず HTML でデザインさせ、その後言語に翻訳させる。アニメーションのチューニング用にスライダーを差し込ませることもある。 - レポート・リサーチ・学習 — Slack、コードベース、git history、Web を横断して合成し、長文 HTML、インタラクティブな解説、スライドにする。SVG で図解させる。 - 使い捨て編集 UI — Linear チケット 30 件をドラッグで Now/Next/Later/Cut に振り分けて「copy as markdown」させる、フィーチャーフラグの設定エディタ、左右並列のプロンプトチューナーなど、その場限りの専用 UI を HTML 1 枚で作らせる。「export」ボタンで結果を Claude にペーストし直せる形にするのがコツ。 - その他、データセット選別、注釈付け、色やイージング曲線・cron 式・正規表現みたいな「言葉で書きにくい値」のピッカー。 よくある質問 - トークン効率悪い？ Markdown より食うのは事実。だが表現力と「実際に読まれる確率」が上がるので結果的に得。Opus 4.7 の 1MM コンテキストなら気にならない。 - Markdown はいつ使う？ ほぼ使わなくなった。 - どう見る？ ブラウザでローカルに開く、または S3 にアップ。 - 生成が遅い？ 2-4倍。だが価値はある。 - バージョン管理は？ 最大の弱点。HTML diff はノイジーで読みづらい。 - デザインがダサくならない？ Frontend design plugin を使う。自社テイストに合わせるなら、コードベースから design system HTML を 1 枚作って参照させる。 Loop に入っている感 結局のところ、HTML を使う本当の理由は「Claude のループに自分が入っている感」だ。プランを深く読まなくなった結果 Claude の判断に委ねるしかなくなる、と恐れていた。HTML にしたらむしろ今までで一番ループに入っている。皆さんもそうあれ。
Markdown has become the dominant file format used by agents to communicate with us. It's simple, portable, has some rich text capability and is easy for you to edit. Claude has even gotten surprisingly good at using ASCII to make diagrams inside of markdown files. But as agents have become more and more powerful, I have felt that markdown has become a restricting format. I find it difficult to read a markdown file of more than a hundred lines. I want richer visualizations, color and diagrams and I want to be able to share them easily. I'm also increasingly not editing these files myself, but using them as specs, reference files, brainstorming outputs, etc. When I do make edits, I'm usually prompting Claude to edit them, which removes one of markdown's largest benefits. I've started preferring HTML as an output format instead of Markdown and increasingly see this being used by others on the Claude Code team, this is why. (examples: https://thariqs.github.io/html-effectiveness) Why HTML? Information Density — HTML can convey much richer information compared to markdown. Tables, CSS design, SVG illustrations, code snippets, JS interactions, workflows, spatial data, images. Almost no information that Claude can read cannot be efficiently represented with HTML. Visual Clarity & Ease of Reading — In practice, I tend to not actually read more than a 100-line markdown file. HTML documents are much easier to read, mobile responsive, navigable. Ease of Sharing — Upload to S3, share link. Most browsers don't render markdown natively. Two-way Interaction — HTML can include sliders, knobs, copy buttons to paste back into Claude. Data Ingestion — Why use Claude Code over ClaudeAI/Claude Design? Because Claude Code can ingest filesystem, MCPs (Slack, Linear), browser, git history. It's Joyful — Making HTML with Claude is more fun and makes me feel invested. How to Get Started Don't make a /html skill. Just ask Claude to "make a HTML file" or "make a HTML artifact". The trick is knowing what you want the artifact to do. Use Cases - Specs, Planning & Exploration — Web of HTML files instead of single markdown plan. Brainstorm, mockups, code snippets, implementation plan, then pass to new session for implementation. - Code Review & Understanding — Render diffs, annotations, flowcharts. Better than default GitHub diff. Attach HTML code explainer to every PR. - Design & Prototypes — Claude Design is HTML-based because HTML is incredibly expressive at design. - Reports, Research & Learning — Synthesize info across Slack, codebase, git, internet into long HTML, interactive explainer, or slideshow. - Custom Editing Interfaces — Throwaway editor: drag-drop ticket triage, feature flag editor, side-by-side prompt tuning, dataset curation, color/regex pickers. FAQ - Less token efficient? Yes, but expressiveness + higher likelihood of reading = better output. With 1MM context in Opus 4.7, not noticeable. - When markdown? Almost never anymore. - How to view? Open locally, or upload to S3. - Slower? 2-4x longer but worth it. - Version control? Biggest downside — HTML diffs are noisy. - Avoid ugly? Frontend design plugin. Or create a design system HTML file from your codebase. Stay in the Loop The real reason: I feel much more in the loop with Claude. Had feared that not reading plans in depth meant leaving Claude to make choices. With HTML, more in the loop than ever.
