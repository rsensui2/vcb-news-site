最初は、見つけるたびに手で直していました。次に、システムプロンプトやCLAUDE.mdのような規約ファイルへ「この表現は使わない」と書き並べました。それでも同じ表現が頻発します。 会話が長くなると指示は薄まる一方です。しかも、モデルが変われば癖の出方も変わります。そのうえ、注意書きを増やすほど、今度は別の場所で別の癖が出てきます。人間の目視だけでは、もう追いつきませんでした。 書いた直後に検査して、書き直させる そこで、書かせる前の注意と併せて、書いた後の機械検査を入れました。使うのは、Claude CodeなどのAIコーディングツールが備えるHooks（フック）という機能です。エージェントの動作の節目に自作のスクリプトを差し込める仕組みで、ファイル編集の直後に発火するものはPostToolUseと呼ばれます。 流れは次のとおりです。 エージェントがファイルを書き込むと、直後にHookが動き、そのファイルをNGワードのルール（正規表現による文字列照合）と突き合わせます。 該当があれば「該当文を丸ごと書き直すこと」という警告が、エージェント自身へ返ります。処理を止めずに直させる点が特徴です。 警告を受けたエージェントが文を書き直すと、その書き込みへもう一度検査がかかります。 セッション終了時にも全体を再検査します。重大な違反が残っている場合、エージェントはそのまま作業を終えられず、該当文を書き直すまで完了報告できません。 こだわった点ですが、語のみ置き換えは禁止しています。NGワードだけを別の語へ差し替えると、同じ問題が別の語形で残り、文章が破綻するからです。だから警告文は「検出箇所を含む文を丸ごと書き直す」ことを求める文面にしました。 ルールは指摘のたびに増やす ルールは、この記事を書いている時点で500本を超えました。一度にまとめて作ったものではありません。 私がエージェントの日本語へ指摘を入れるたび、その場で少しづつ増えていきました。指摘をルールへ登録するSkill（エージェントへ手順を教える仕組み）を作ってあるので、私が指摘すると半ば勝手に登録されていきます。加えて、週に1回ほど、会話履歴をエージェント自身に分析させて、繰り返し直している表現をまとめて登録しています。 禁止だけを並べると、エージェントは避け方が分からず、不自然な回避文を書きがちです。グッドパターンを添えるようにしてから、書き直しの精度が上がっています。 シーンごとにルールのオンオフも変えています。たとえば造語（「◯◯メソッド」のような自分で作った言葉）の検査は、ビジネス文書ではオン、小説ではオフです。なぜなら造語は創作では技法だからです。 文書全体の集計で見つかる癖もある 単語の照合だけでは拾えない癖は、文書全体の集計で検出します。 同じ文末（ます・です・ましたなど）が3文以上続いたら検出する です・ます調と常体の混在を、文末の分布を集計して検出する 比喩表現が同じ行や同じ文書内に重なったら、重ね使いとして警告する AIコンサルの現場で、経営者からよく聞かれる質問があります。 「Claude Codeのセキュリティ、結局どうすればいいですか?」 こちらに対しては、メルカリ社が、2026年4月10日、メルカリ本社(六本木ヒルズ森タワー26階)で開かれた「Claude Code Meetup Japan #4」というエンジニア向けの勉強会での「Claude Codeセキュリティ設定の組織配布戦略」という発表資料が非常に参考になります。 この発表資料は、個人のAIコンサルタントが「経営者・情シス・PM全員が読むべき内容」と紹介し、金融業界でAI推進をしている書き手が「これをベースに、銀行だったら何を足すか」を考察し、他にも複数のブログが同じスライドを題材に記事を書いています。1社の社内発表が、これだけ広く参照されるのは珍しいことだと思います。 そこで今回は、この発表そのものの中身に加えて、「なぜこの話がここまで広がったのか」「発表のあとに何が起きているのか」まで、僕なりに調べて整理してみました。単に設定をコピペするだけでなく、その裏側まで理解しておくと、自社に応用するときの判断がしやすくなるはずです。 そもそも、なぜ今このテーマが刺さるのか 背景には、AIの性質そのものの変化があります。これまでのChatGPTのようなAIは、人が質問して、AIが答えるだけの「対話型」でした。一方Claude Codeは、AI自身がファイルを読み書きし、コマンドを実行し、ネットにも取りに行く「自律型(エージェント型)」です。 この違いは大きいです。対話型のAIなら、変な回答をされても実害はコピペする前に人間が止められます。でも自律型のAIは、AI自身がもう手を動かしてしまっているので、気づいたときには何かが実行された後、ということが起こり得ます。 Claude Codeの利用が非エンジニアにも広がり始めた今、多くの経営者が「便利なのは分かるけど、何がどこまで起こり得るのか分からない」という状態で足踏みしています。メルカリの発表は、この漠然とした不安に、実際の設定という具体的な答えを出した。だからこそ刺さったのだと思います。 何が「怖い」のか、具体的な話をします メルカリの発表では、想定すべき最悪のシナリオとして「誤ったrm -rf(削除コマンド)の実行」と「curl(外部通信コマンド)経由の情報漏洩」の2つが挙げられていました。抽象的な話に聞こえるかもしれませんが、これは決して大げさな心配ではありません。 2026年に入ってから、Claude Code自体にも実際の脆弱性が報告されています。セキュリティ専門機関のCheck Point Researchが公表した脆弱性のひとつでは、悪意のある第三者が用意したリポジトリ(コードの保管場所)を開くだけで、確認画面が出る前に不正なコードが実行されてしまう問題が指摘されました。また別の脆弱性では、接続先の設定を書き換えることで、認証情報が外部のサーバーに送られてしまう経路も見つかっています。いずれもClaude Code側で修正版が配布されていますが、「知らない相手が作ったフォルダを、何の確認もなく開く」という何気ない行動が、事故の入り口になり得ることが分かります。 ちなみに、こうした攻撃への防御は現状まだ発展途上です。AIエージェントに対する巧妙な"命令の混ぜ込み"(プロンプトインジェクション)は、最先端の防御を持ってしても防ぎきれないケースが多いと報告する研究もあります。この手の数字は書き手によってばらつきがあり、僕自身も一次の論文までは確認しきれていないので、正確な数値として鵜呑みにはしていません。ただ、「AIが自力で悪意ある指示を見抜いてくれる」という期待は、今の時点では持たないほうがいい、という方向性は複数の情報源で一致しています。 メルカリが実際にやったこと 発表の中身自体は、意外とシンプルです。要点だけ振り返ります。 確認を全部スキップする危険なモードを、管理者設定で使えなくする curlやwgetのような外部通信系のコマンドは拒否リストに入れるか、実行前に必ず確認させる .envファイルやSSHキーなど、秘密情報が入ったファイルは読み取り自体を禁止する sandbox機能で、作業フォルダの外や許可していないネット先には物理的に触れられなくする CLAUDE.mdという指示書ファイルに、会社としてのセキュリティ方針を書いておき、AIに毎回読ませる ここまでは「よくできた設定集」の話です。でも、他の書き手の分析を読んでいて、僕がなるほどと思ったのは、この設定の中身そのものより「誰にどう配るか」という設計のほうにあります。 本当に効いていたのは、設定の中身より「配り方」 メルカリは、この設定をMDM(会社が社員のパソコンを一括管理する仕組み。メルカリではJamfというツールを使っています)経由で全社員に配っています。ポイントは、配る内容を一律にしなかったことです。 エンジニアには、安全性を保ちつつ、ある程度カスタマイズできる設定 エンジニア以外の社員には、いじる余地をほぼ残さない、いちばん厳しい設定 同じClaude Codeというツールでも、使う人によって必要な自由度がまったく違います。エンジニアにとっては「安全を保ちながら生産性を落とさないこと」が大事ですが、非エンジニアにとっては「そもそも触って壊れないこと」のほうが大事です。この2つを1つの設定で両立させようとすると、たいてい中途半端になります。属性ごとに違う「安全な初期値」を配る、という発想の転換が、この発表がただの設定集で終わらなかった理由だと思います。 これは実は、Claude Codeに限った話ではありません。今後、CodexやCursor、他のAIエージェントを会社に入れるたびに、同じ論点が繰り返し出てくるはずです。AI導入の競争は、そのうち「どのAIが賢いか」ではなく「どう安全に統治するか」に軸足が移っていく。そんな予感がします。 この発表は、あくまで入り口 もうひとつ紹介したいのが、この発表をベースに、金融業界向けの設計を独自に考察していたエンジニアのブログです。金融機関でAI推進をしているという書き手が、「メルカリの発表は端末・設定レベルとしては十分。ただ金融機関では、その上にさらに3つの層を積み上げる必要がある」という整理をしていました。 端末・設定層: メルカリの発表がカバーしている範囲(MDMでの設定配布など) インフラ・契約層: どの経路でAIに接続するか(例えば海外のサーバーを直接使わず、国内リージョンを経由する構成にするなど) 監査・コンプライアンス層: 誰が・いつ・何をAIに入力したかを、何年分残しておくか ガバナンス層: 経営レベルでの承認体制や、規制当局への説明責任 金融機関ほど厳格な業界の話ではありますが、この「層で考える」という視点自体は、規模の大きくない会社にも役立ちます。今日やるべきなのは一番下の層(設定を配ること)で十分ですが、「その上にはこういう層がある」と知っておくだけで、事業が大きくなったときや、扱うデータの機密性が上がったときに、何を足せばいいか判断しやすくなります。 中小企業なら、ここから始める 最小セットは、こちらです。 { "permissions": { "disableBypassPermissionsMode": "disable", "deny": [ "Bash(curl:)", "Bash(wget:)", "Bash(sudo:)", "Read(.env)", "Read(.env.)", "Read(/.ssh/)" ], "ask": [ "Bash(git push:)", "Bash(rm:)" ] } } これを.claude/settings.jsonという名前で保存し、Claude Codeを使うフォルダの直下に置くだけで動きます。会社全体に強制したいなら、ホームフォルダ直下の~/.claude/settings.jsonに置いてください。 そのうえで、社員が複数いるなら、いきなり全員に同じ設定を配るのではなく、「エンジニア(または業務でコードを触る人)」と「それ以外」で、渡す設定の厳しさを変えることをおすすめします。難しく考える必要はなく、非エンジニア向けには上のdenyリストをさらに厚くする、くらいの調整で十分です。 落とし穴: この手の"教科書"を真似るときに気をつけたいこと ネットに出回っている設定のコピペをそのまま信じない。今回いろいろな記事を読み比べていて気づいたのですが、同じ「確認スキップを禁止する設定」でも、記事によってキー名の書き方が微妙に違いました。僕が確認した限り、Anthropic公式ドキュメントに載っているのはdisableBypassPermissionsModeという名前です。人づてに広がるうちに、正確な情報が少しずつ崩れていくことがあるので、最終的には必ず公式ドキュメントで裏を取ることをおすすめします。 「メルカリがやっているから安全」で思考停止しない。メルカリの設定は、あくまでメルカリの事業内容・扱うデータ・組織規模を前提にした設計です。自社が扱う情報の機密性や、業界の規制によっては、もっと厳しい設定や、逆にもっと緩い運用でも十分な場合があります。 設定を配って終わりにしない。設定という「物理的な鍵」と、判断力を育てる「教育」は両輪です。どちらか一方だけでは、いずれどこかで隙ができます。
