dead」という議論が出てきた理由 こうした変化を背景に、海外では「SaaS is dead」という議論も出ています。 象徴的なのが、Microsoft CEOのSatya Nadellaです。 Nadellaは2024年12月、現在の業務アプリケーションについて、 「CRUD databases with a bunch of business logic」 と表現しました。 簡単に言えば、 データベースがあって、その上に業務ルールが載っている。 CRMであれば、 顧客がいる。 商談がある。 タスクがある。 その上に、 「商談がこの状態になったら担当者へ通知する」 「このデータはこの社員だけが見られる」 「受注したら次の処理を実行する」 という会社ごとの業務ロジックがあります。 Nadellaが予測しているのは、この業務ロジックの多くがAIエージェント側へ移っていくことです。 AIが複数のデータベースを横断し、判断し、データを書き換え、仕事まで行うのであれば、現在の「業務アプリケーション」という単位そのものが崩れていく可能性がある、と話しています。 ただ、私はSaaSそのものがなくなるとは思っていません。 むしろ、既製ソフトウェアを買う動きも強く残っています。 Andreessen Horowitzが2025年に100人のCIOを調査したところ、生成AI市場の初期には企業が自分たちでAIアプリを作る傾向が強かった一方、その後は成熟したAIアプリを外部から購入する動きも強まっていました。 理由の一つが、 自社で作ったAIツールは保守が難しく、必ずしも競争優位につながらない ことです。 Gartnerも2026年8月、AIコードアシスタントやAIコーディングエージェントによってアプリを自社開発する選択肢が現実的になった一方、BuildかBuyかは単純な二択ではなく、業務ごとに判断する必要があるというフレームワークを公開しています。 つまり、 「SaaSが死ぬ」 というより、 「SaaSを買うしかなかった時代が終わる」 と考える方が近いのではないでしょうか。 会計、給与、決済、電子契約など、標準化されていて、制度や外部仕様への継続的な追従が必要な領域は、既製SaaSを利用する方が合理的でしょう。 一方で、 自社独自の案件管理。 自社独自の見積フロー。 自社独自の顧客対応。 自社独自の受発注。 自社独自の承認業務。 こうした領域まで、既製SaaSに仕事を合わせる必要はなくなってきています。 「作れる」と「持ち続けられる」は違う ただし、ここには大きな問題があります。 保守運用です。 AIに、 「案件管理システムを作って」 と頼めば、画面や基本的な機能はかなり簡単に作れるようになりました。 しかし本番で使うなら話は別です。 どこでプログラムを動かすのか。 データベースはどうするのか。 バックアップはどうするのか。 メールはどう送るのか。 定期処理はどうするのか。 処理に失敗したらどう再実行するのか。 アクセス権限はどう管理するのか。 外部からの攻撃をどう防ぐのか。 AIがコードを書けるようになっても、ここを人間が全部管理するなら、 「結局、自社開発は保守が大変」 という従来の結論に戻ってしまいます。 だからAI時代のソフトウェア開発では、Claude Code、Codex、CursorのようなAIコーディングツールだけを見ても不十分だと思っています。 必要なのは二つです。 AIによって、自社に必要なソフトウェアを簡単に作れること。 そして、 作ったソフトウェアを、人間がほとんどインフラ運用せずに持ち続けられること。 前者は、かなり実現し始めています。 では後者はどうでしょうか。 そこで注目しているのが、 Cloudflare + Turso という構成です。 Cloudflareなら「サーバーを持つ」がほぼ消える Cloudflare Workersは、Cloudflareが提供するサーバーレス実行環境です。 従来のWebシステムなら、 アプリケーション ↓ Webサーバー ↓ OS ↓ ランタイム ↓ ネットワーク ↓ ロードバランサー まで考える必要がありました。 Workersなら、かなり乱暴に言えば、 コード ↓ Cloudflare です。 サーバーを何台立てるかを考えなくていい。 OSを管理しなくていい。 負荷が増えたからサーバーを追加する、といった運用も基本的にはありません。 そして価格も小規模システムには使いやすい設計です。 Workers Paidの基本料金は月5ドルで、標準料金には月1,000万リクエスト、3,000万CPUミリ秒が含まれています。 さらにPaidプランでは、1アカウントあたり500 Workersまで作ることができます。 500個あれば、多くの企業の自社用システムでは十分でしょう。 たとえば、 案件管理 見積管理 問い合わせ管理 採用管理 在庫管理 受発注管理 日報 顧客管理 を全部一つの巨大な基幹システムに詰め込む必要もありません。 小さなソフトウェアとして分割してしまう。 という考え方ができます。 これはAIとの相性もいいと考えています。 巨大なコードベースをAIに理解させるより、小さなシステム単位で、 「このフォームを変えて」 「この業務フローを追加して」 と指示できるからです。 データベースも「一つをみんなで使う」をやめられる 次に問題になるのがデータベースです。 これまでのSaaSでは、一つのアプリ、一つのデータベースの中に複数企業を入れるマルチテナント構成が一般的でした。 1つのアプリ ↓ 1つのDB ↓ A社 B社 C社 各テーブルに、 tenant_id のような項目を持たせ、 A社の社員がB社のデータを取得しないように、 権限管理。 Row Level Security。 クエリ条件。 データ分離。 などを慎重に設計します。 もちろん、何万社も利用する巨大SaaSでは合理的です。 しかし、AIによって小さなソフトウェアそのものを大量に作れるのであれば、 なぜアプリもデータベースも共有する必要があるのでしょうか。 そこでTursoです。 Tursoなら「1社1DB」が現実的になる Tursoは、多数の独立したデータベースを持つ設計を前面に出しています。 公式にも「Database Per Tenant」というユースケースがあり、顧客ごとに独立したDBを持たせ、複雑な権限ロジックを減らす設計を紹介しています。 さらに2026年5月から、Tursoの有料プランではDatabase数だけでなく、Active Database数の上限もなくなりました。 現在の料金は、 Free：100 databases Developer：Unlimited databases Developer：月4.99ドル Storage：9GB Rows Read：月25億 Rows Written：月2,500万 となっています。 すると、 A社 → Worker A → Turso DB A B社 → Worker B → Turso DB B C社 → Worker C → Turso DB C という構成が現実的になります。 マルチテナントを「うまく作る」必要がなくなるかもしれない これは設計思想としてかなり大きな変化です。 従来は、 1つのソフトウェアと1つのDBを、どう安全に100社で共有するか を考えていました。 これからは、 100社なら100個の小さなソフトウェアと100個のDBを、どう管理するか を考える方がシンプルになるケースがあります。 A社のDBにはA社のデータしかない。 B社のDBにはB社のデータしかない。 そもそも混ざっていなければ、 「A社のユーザーが間違えてB社の行を取得してしまう」 という問題そのものを減らせます。 もちろん共通化した方がよいコードや仕組みは共通化します。 重要なのは、 マルチテナント＝すべての顧客を一つのアプリと一つのDBに入れること ではなくなるということです。 自社用システムならTursoで十分なケースは多い ここで、 「SQLite系のDBで本当に業務システムを作って大丈夫なのか」 という疑問もあると思います。 当然、すべてのシステムにTursoを使えばいいという話ではありません。 極端に書き込み量が大きなシステム。 PostgreSQL固有の高度な機能へ大きく依存するシステム。 巨大なデータウェアハウス。 こうした用途には別の選択肢があります。 しかし、 社員30人。 営業10人。 顧客1万件。 案件10万件。 という自社用の案件管理システムならどうでしょうか。 Developerプランだけでも、月25億Rows Read、月2,500万Rows Writtenがあります。 世界中の何百万人がアクセスするサービスを作るわけではありません。 普通の会社の業務システムに、本当に巨大なDBクラスタが必要なのか。 というところから考えてもいいと思います。 AI開発で後から欲しくなるものもCloudflareに揃っている 業務システムは、最初は単純です。 顧客を登録する。 案件を登録する。 一覧を見る。 しかし使い始めると、必ずやりたいことが増えてきます。 「毎晩集計してほしい」 「3日後にメールを送ってほしい」 「AIで内容を判断してほしい」 「APIに失敗したら再実行してほしい」 「上司が承認したら次へ進んでほしい」 このタイミングでインフラが複雑になりがちです。 Cloudflareには、このための部品も用意されています。 Workflows Cloudflare Workflowsは、複数ステップにまたがる処理を実行する仕組みです。 処理途中の状態を保存し、失敗したタスクを自動で再実行できます。 数分だけでなく、数時間、数日、数週間にまたがる処理も扱えます。 Cloudflare自身も、AIアプリケーション、データ処理、メールを含むユーザーライフサイクル、人間の承認を含む処理などをユースケースに挙げています。 たとえば、 問い合わせ受付 ↓ AIが内容を分類 ↓ 企業情報を調査 ↓ 担当者を決める ↓ 上司の承認を待つ ↓ 顧客へ返信 という業務を、一つのWorkflowとして実装できます。 Queues もっと単純に、 「今すぐ処理する必要はないので、裏側でやってほしい」 という仕事にはQueuesがあります。 問い合わせ登録 ↓ 画面にはすぐ「登録完了」 ↓ Queueへ投入 ↓ AI分析 ↓ Slack通知 ↓ メール送信 Cloudflare Queuesは、標準でat-least-once deliveryを提供しています。 つまりメッセージを失わないことを優先し、少なくとも1回は配送する設計です。 Durable Objects チャット、リアルタイム通知、共同編集、AIエージェントなど、ユーザーやプロセスごとに状態を持つ必要があればDurable Objectsがあります。 Durable Objectsは、計算処理と永続ストレージを組み合わせた、状態を持つサーバーレスの仕組みです。 Cloudflareはチャット、共同編集、ライブ通知、AIエージェントなどを代表的な用途として挙げています。 つまり、 状態を持つためだけに別のRedisや調整用サーバーを用意する といった構成を減らせるケースがあります。 Email Service 業務システムを作っていると、もう一つ必要になるのがメールです。 問い合わせを受信する。 注文確認を送る。 見積完了を通知する。 担当者へ知らせる。 顧客から返信を受け取る。 Cloudflareでは2026年4月からEmail SendingがPublic Betaとなり、Email Routingと合わせて、Workersからメールの送受信を扱えるようになっています。 HTML、テキスト、添付ファイル、インライン画像などを含むトランザクションメールをWorkersから送信できます。 受信メールもWorkerのemail() handlerへ渡し、プログラムから転送、返信、拒否などを処理できます。 すると、 support@example.com ↓ Cloudflareでメール受信 ↓ Worker ↓ AIが内容を読む ↓ Tursoから顧客履歴を取得 ↓ 返信案を生成 ↓ 必要なら人間が確認 ↓ メール返信 というシステムも作れます。 さらにAgents SDKもEmail Serviceに対応しており、AIエージェントがメールを受け取り、返信し、その返信を既存のセッションへ戻して会話を続ける仕組みまで用意されています。 Workers Paidでは外部宛てメールが月3,000通まで含まれ、それを超えると1,000通あたり0.35ドル。 Email Routingによる受信はFree、Paidともに無制限です。 社内システムならZero Trustで閉じればいい もう一つ、自社システムを作ると必ず出てくるのが、 セキュリティは大丈夫なのか という話です。 社内システムなら、そもそも誰でもログインできるサービスにする必要はありません。 Cloudflare Accessを前段に置けば、 社員 ↓ Google Workspace / Microsoftなどで認証 ↓ Cloudflare Access ↓ 自社システム という構成にできます。 すべての社内システムで、 ログイン機能を自作する。 パスワードを管理する。 退職者のアカウントを個別に止める。 ということをする必要はありません。 CloudflareのZero Trust Freeプランは50ユーザーまで0ドルで利用できます。 社員数十人の企業が自社システムを作るなら、かなり相性のいい仕組みです。 「作った後が大変」がかなり減っている ここまでを並べてみます。 以前なら、 アプリケーション ↓ サーバー ↓ DBサーバー ↓ バックアップ ↓ ジョブサーバー ↓ キュー ↓ 状態管理 ↓ メール ↓ 認証 ↓ 監視 まで考える必要がありました。 今なら、 アプリ実行 → Cloudflare Workers データ → Turso 長時間・複数ステップ処理 → Workflows 非同期処理 → Queues リアルタイム・状態管理 → Durable Objects メール → Cloudflare Email Service アクセス制御 → Cloudflare Zero Trust と、かなりの部分をマネージドサービスへ任せられます。 もちろん、保守が完全になくなるわけではありません。 仕様変更はあります。 業務フローも変わります。 AIが生成したコードのレビューも必要です。 データ設計を間違えることもあります。 アプリケーション固有のセキュリティについては、自分たちで考えなければいけません。 それでも、 OSをアップデートする。 サーバー容量を監視する。 DBサーバーを再起動する。 キューサーバーを運用する。 といった、 インフラを所有することで発生していた保守 はかなり減らせます。 ここが、AIコーディングだけを見た場合との大きな違いです。 本当に作った後まで簡単なのか。Codexに顧客管理システムを作らせてみる ここまで、 「AIで作れる」 「Cloudflareなら運用も減らせる」 と書いてきました。 では、本当にできるのでしょうか。 実際にやってみましょう。 今回はシンプルな顧客管理システムを作ります。 機能は、 顧客一覧 顧客登録 顧客編集 顧客削除 顧客検索 商談ステータス メモ 程度です。 技術構成は、 Frontend React TanStack Router TanStack Query API Hono Runtime Cloudflare Workers Database Turso とします。 ここで重要なのは、手でプロジェクトを作らないことです。 必要なコマンドも含めて、Codexへ全部指示します。 Tursoだけ先に用意する 今回TursoはCloudflareとは別サービスなので、CloudflareのTemporary AccountからTursoアカウントまで作られるわけではありません。 TursoのDBだけ先に作っておきます。 turso db create customer-manager URLを取得します。 turso db show customer-manager --http-url 認証用トークンも作ります。 turso db tokens create customer-manager Turso公式もEdgeやServerless Runtimeでは@libsql/client/webを使い、URLとAuth TokenからHTTP接続する方法を案内しています。 この2つを、 TURSO_DATABASE_URL TURSO_AUTH_TOKEN として用意しておきます。 これだけです。 Codexにこのプロンプトを渡す 以下を、そのままCodexへ渡します。 顧客管理Webアプリケーションを作成してください。 設計だけで終わらず、 コード作成、依存関係のインストール、DB初期化、 テスト、Cloudflare Workersへのデプロイまで実行してください。 外部サービスの認証情報が不足していて 技術的に進められない場合を除き、確認質問は不要です。 使用技術 - TypeScript - React - Vite - TanStack Router - TanStack Query - Hono - Cloudflare Workers - Cloudflare Vite Plugin - Turso - @libsql/client/web フロントエンドはReact + TanStack Router + TanStack Query、 APIはHonoとしてください。 ReactフロントエンドとHono APIを 1つのCloudflare Workerから配信してください。 作るもの シンプルな社内向け顧客管理システムです。
