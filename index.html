Cloudflareが「Cloudflare OS」をオープンソースで公開しました。 ソースコードを手元にcloneして実際に動かしてみたら、これは単なる社内ツールの公開じゃなく、「会社でAIをどう使うか」の設計図そのものでした。今日はコードの中身まで踏み込んで解説します。 結論から言うと、これは「社員にChatGPTを配る」の、次のフェーズの話。AIを業務に入れたい会社は関係してきます。 Cloudflare OSとは何か ・Cloudflare社内で、エンジニアから営業まで数千人が毎日使っている「会社でAIを安全に使い倒す基盤」の公開版 ・エージェントにタスクを頼むチャット、AIに業務アプリを作らせる仕組み、権限管理の3つがワンセット ・「うちの会社用にコピーして『自社OS』にしてくれ」というスタンスでの公開 普通のOSではありませんが、Cloudflare自身が「OS」と呼ぶ理由があります。実際にソースを開くと、バックエンドが「カーネル」、外部サービス連携が「デバイスドライバ」、AIが作るアプリが「プロセス」という構造で作られている。会社のAI活用を、OSがコンピュータを管理するのと同じ思想で管理しにきています。 「Gadget」という考え方 ここが大事なポイント。 ・「スライドを作って」と頼むと、自分専用のスライドアプリのインスタンスがサンドボックス内に生成される ・全ユーザーが自分のコピーを持つので、アプリのバグで他人のデータが漏れる構造がそもそも存在しない ・機能が足りなければ「この機能を足して」と言うだけ。他人に影響しないから、自由に改造していい これは、この25年の「中央のSaaSにみんなで接続する」モデルの逆張りです。 今までは、アプリを作った人がサーバーでホストして、全員がそこに接続していた。Cloudflare OSはスマホアプリに近くて、全員が自分のコピーを動かす。だから、機能要望を出して開発者が対応するのを待つ必要がない。ユーザーが自分でAIに頼んで直せる。 「AIが誰でも開発者にした」という前提に立つと、中央集権的なソフトウェアの形が意味をなさなくなる、という設計になっている。 セキュリティ層「Gatekeeper」 エージェントに社内のGitHubやNotionを触らせたい。でも情報漏洩が怖い。この板挟みへの回答が、Gatekeeperという仕組みです。 ・エージェントもアプリも、初期状態では何の権限も持たない。GitHubリポジトリなどのリソースを「紹介」して初めて、そこだけ触れる ・全操作がログに残り、副作用のある操作は人間の承認待ちになる ・MCPのように全ツールを最初から見せる方式と違い、その場の仕事に必要な分だけを渡す コードを読んで一番感心したのが、承認の仕組みです。 普通の「人間が承認するまでAIが止まる」方式だと、エージェントに仕事を頼んで離席し、戻ってきたら最初の1ステップの承認待ちで止まっていた、が起きる。だから人は「面倒だから全部自動承認」に逃げて、危険な運用になる。 Cloudflare OSは違って、承認待ちの操作は結果をシミュレートして、エージェントを先に進ませる。人間は後でまとめて承認・却下すればいい。「高リスクな操作はエージェントが提案し、人間が決める」。この線引きが、一時しのぎではなく恒久的な正解として設計されています。 手元で動かしてみた 実際に手元にcloneして試してみました。 ・pnpm run-local だけでローカルで立ち上がって、ブラウザで触れる ・同梱の外部サービス連携（Gatekeeper）は16種類。GitHub、Google、Notion、Slack、Supabase、Linear、Confluence、スケジューラなど、サービスごとに権限管理の実装が分かれている ・本番は自分のCloudflareアカウントに数分でデプロイできる導線もある 作りを追うと、認証まわりの徹底ぶりが目立ちます。 誰がサインインできるかの設定だけは、管理画面からいじれないよう、あえて環境変数側に固定してある。 「管理者アカウントが乗っ取られても、認証設定だけは変えられない」ための設計です。 なぜこれが「事業の話」なのか 多くの会社のAI活用は、今こういう状態です。 ・社員にChatGPTやCopilotのアカウントを配った ・でも各自がチャットで使うだけで止まっている ・実データに触らせたりアプリを作らせようとすると、情報漏洩が怖くて情シスが止める Cloudflare OSが示しているのは、その次のフェーズです。 ・社員がAIに「自分専用の業務アプリ」を作らせる ・作ったアプリが社内に増えていく ・それを、権限ゼロから必要な分だけ渡す仕組みの上で、安全に回す 「社員にAIを配る」の次は、「社員が作ったAIアプリが社内に溢れる」フェーズが来る。そのとき効いてくるのは、高機能なAIそのものより、それを暴走させずに管理する土台です。 そしてその参考実装が、実際に数千人で運用された状態で、無料で全部読める。これがこの公開の一番の価値だと思っています。 まとめ ・Cloudflare OSは、社内でAIを安全に使うための基盤をまるごとオープンソース化したもの ・核は「Gadget」。全員が自分専用の業務アプリのコピーを持ち、AIに自由に改造させられる ・「Gatekeeper」で、権限ゼロから必要な分だけ渡す。承認待ちでも止まらない設計が秀逸 ・まだアーリーアクセス段階。ただし「会社のAI化」の設計思想として、今読む価値がある 去年、AIにどう仕事をさせるかを設計する仕事が生まれた。次は、社員全員がAIとどう働く場所を作るかを設計する仕事が生まれます。 その最初の完成形が、いま無料で公開されています。

Part 1（親ポスト） 8月14日から、Claude Code の Pro、Max、Team ユーザーでは Auto mode が既定の権限モードになります。 Auto mode は、シェルコマンドと操作を別の分類器で審査します。テストでは危険なコマンドの89%を検出しました。手動承認で検出できたのは14%でした。 Part 2 手動承認より信頼できると考える理由の1つがあります。1,053人の有料テスターを対象とした調査で、権限確認プロンプトの文章を明らかに危険なコマンドへ差し替えました（文章を表示しただけで、実際には何も実行していません）。 テスターが危険性を見抜いた割合は13.6%で、50回プロンプトを見た後には約5%まで低下しました。Auto mode はその危険なコマンドを遮断しました。 Part 3 この変更を行う理由は2つあります。 1. 私たちが追跡したすべての安全指標で、Auto mode は手動の権限確認と同等か、それを上回りました。 2. 長時間にわたる作業がより現実的になります。Claude が中断されずに長く動けるので、数時間規模のタスクを実行できます。 Part 4 Auto mode はツール呼び出しのたびに分類器を動かすため、少量の追加トークンを使います。 本日から、この分類器のオーバーヘッドは Pro、Max、Team プランの利用上限に算入されません。Auto mode が利用可能になった後、Enterprise プランと API ユーザーにもこの変更を適用します。 Part 5 Auto mode は Opus 5 のような長時間タスクに優れたモデルとも相性が良いです。モデルは数時間規模のタスクを計画・実行できますが、ツール呼び出しのたびにセッションが止まり、人間を待っていたのでは、その能力を活かせません。 Part 6 既定モードが切り替わるときは、アプリ内で通知します。既に既定の権限モードを設定している場合、Claude は何かを変更する前に確認します。Shift+Tab でいつでもモードを切り替えられます。 管理者は managed settings で defaultMode を固定でき、Auto mode を完全に無効化することもできます。 Part 7 ブログ全文: https://t.co/m0wkp0C5k6
