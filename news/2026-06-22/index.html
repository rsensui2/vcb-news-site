shadcn-labs、AIエージェント版「agentcn」を公開 — ワンコマンドでエージェント雛形

shadcn/ui で知られる shadcn-labs が、AIエージェントをワンコマンド・ゼロコンフィグで導入できる「agentcn」を公開した。Vercel の Eve と Flue を土台に、production-ready なエージェント・レシピを shadcn/ui と同じ「コピーして自分で所有する」流儀で配布する。shadcn 本人は「エージェントとは instructions / tools / skills / subagents / channels / schedules / config の合成物」と定義し、それを部品として組み立て可能にする思想を示している。

キーポイント

  • agentcn = shadcn/ui のエージェント版。ワンコマンドで雛形を取得し自分のコードに「所有」する方式
  • Vercel の Eve と Flue 上に構築、shadcn/ui 互換、ゼロコンフィグ
  • shadcn の定義: エージェント＝指示・ツール・スキル・サブエージェント・チャンネル・スケジュール・設定の合成物
  • リポジトリ公開: github.com/shadcn-labs/agentcn
エージェントを「スクラッチで書く」段階から「実証済みレシピを取り込んで所有・改変する」段階へ移す試み。shadcn/ui が UI で起こした標準化を、エージェント構築でも狙う動き。

自己検証ループ — スウォームを「ループの1ステージ」にして幻覚を潰す

「エージェント・スウォーム（大量並列）は自信満々のゴミを返す」という前提に立ち、スウォームをゴールではなく検証ループの1ステージにする設計を解説した X Article。Opus 4.8 が計画と検証、Kimi K2.6 スウォームが実行を担い、Opus が各出力を出典と突き合わせ、合わない数値・解決しない引用を却下してキューに戻す。却下がゼロになるまでループが止まらない。

キーポイント

  • 検証なしスウォームの品質＝最悪のエージェントの品質。97体が正しくても3体が幻覚すれば完成物は完璧版と見分けがつかない
  • 4ステージのサイクル: ①Opus が計画 ②スウォームが実行 ③Opus が出典照合で検証 ④却下分を理由付きで再実行
  • 実行ログ: 1回目で100社中12社却下 → 2回目3社 → 3回目ゼロでループ自律停止
  • 厳格な検証は Binance / Yahoo Finance / World Bank / IMF / ライブ株式の5フィードと実数照合で成立
  • 結論「スウォーム＝速さ、ループ＝信頼できる速さ」。差分は verify ステップ
並列エージェントを実務に入れる核心＝「量を増やすと誤りも同率で増える、価値を生むのは独立した検証ステージ」を具体例で示す。writer と checker を分け、却下ゼロまで回すパターンはそのまま流用できる。

エージェント設計 / @SAIRAHUL1 / X ARTICLE / BOOKMARK

メモリファイルで「忘れない」AIエージェントを作る — 5つのファイル構成

AIエージェントが失敗するのはモデルが悪いからではなく「毎セッション記憶喪失で目覚める」から、という問題提起。CLAUDE.md・AGENTS.md・CLAUDE.local.md・MEMORY.md・README.md の5ファイルでエージェントに永続的な文脈を与える設計を解説する。結論は『Model + Memory + Retrieval + Feedback = 有用なエージェント』で、記憶こそ複利で効く変数だと位置づける。

キーポイント

  • CLAUDE.md=Claude 専用 briefing（文脈/コード規約/コマンド/アーキの4節、目標300行未満）
  • AGENTS.md=ベンダー横断標準（Cursor / Copilot / Gemini CLI / Windsurf / Aider / Zed が読む）
  • CLAUDE.local.md=個人の好み（git 非コミット）、MEMORY.md=AI が自分で書く auto-memory
  • @imports で巨大1枚岩を回避（最大5階層）、`/init` で生成→大半を削るワークフロー
  • 結論の式: Model + Memory + Retrieval + Feedback = 有用なエージェント。記憶は複利、モデルの賢さは複利でない
Claude Code を「使い捨てツール」から「昨日を覚えるチームメイト」に変える最初の一歩。CLAUDE.md / AGENTS.md / MEMORY.md の書き分けは初心者がつまずく典型ポイントで、そのまま実務テンプレになる。

プロンプトから「ループ工学」へ — 本番で動くエージェントループの実戦ガイド

「もうプロンプトを打つな、エージェントにプロンプトを打つループを設計しろ」(Steinberger / Cherny) という主張を本番設計に落とした実戦ガイド。ループを構成する6部品と、Claude Code の /goal を契約として書く方法、そして『コストの所在が単発呼び出しからループの周回数へ移った』ことを具体例で示す。

キーポイント

  • ループは5つの意味を持つ: ReAct→AutoGPT→ralph loop→/loop・/goal→orchestration
  • ループの6部品: trigger / isolation(git worktree) / 書き留めた context / tools への reach / 独立した検証者 / disk上の state
  • 具体例『PR babysitter』: 15分毎・1試行5分10ファイル・CI緑か予算切れで停止
  • /goal は終了状態・証拠・制約・予算の4つを契約のように明示する
  • コストは iterations が予算項目。弱い検証者が最も高コストなバグ、早く失敗するのがコスト管理
「プロンプト職人」を卒業した受講者が次に登る階段の地図。/loop と /goal の違い、6部品、PR babysitter の具体パラメータがそのまま課題テンプレになる。

DESIGN.md をエージェントに先に与えて UI のスタイル崩れを防ぐ

AI に UI を作らせると毎回スタイルが微妙にズレる問題への処方箋として、Google Stitch 由来の DESIGN.md を紹介する。color / type scale / spacing / radius / shadow / コンポーネント規則を plain text 化したデザインシステムを、UI ビルド前に毎回読ませてドリフトを止める手法。

キーポイント

  • DESIGN.md = 色・タイプスケール・余白・角丸・影・コンポーネント規則を平文化したデザインシステム
  • 役割分担: AGENTS.md=どう作るか(how to build)、DESIGN.md=どう見えるべきか(how it should look)
  • Stripe / Linear / Airbnb / Vercel など実在73個を集めたリポジトリを雛形に流用できる
  • ルートに1枚置いて「全UIを DESIGN.md に従わせろ」と指示するだけ
Claude Code / v0 / Cursor で UI を作ると画面ごとに余白も角丸もバラバラになりがちな典型課題への即効薬。メモリファイル論と同じ「エージェントに読ませる文脈ファイル」の引き出しが増える。
