Anthropic、Fable 5 のアクセスを 7/19 まで再延長 — Claude Code の週次上限50%増も継続

Anthropic 公式が、全有料プランでの Claude Fable 5 アクセスを 7月19日まで延長すると発表した。あわせて Claude Code の週次レート上限を50%引き上げた措置も同日まで維持する。7/08 の告知（当初は 7/12 まで）からの再延長で、期限の後ろ倒しが繰り返されている形だ。

キーポイント

  • 対象は全有料プラン。Fable 5 アクセスの期限が 7月19日まで延長
  • Claude Code の週次レート上限50%増も 7/19 まで継続
  • 続報ポストで「週次上限の最大50%までを Fable 5 に充当でき、超過後は usage credits 購入か別モデル切替で継続」と補足
  • 7/08 告知（7/12 期限）からの再延長。恒久措置ではなく、7/19 以降は元の条件に戻る前提
  • Likes 7.2万・Views 2,400万・リプライ 6,559 件と、通常のモデル告知を大きく超える反響
「7/19 までは Fable 5 と上限50%増が使える」という実務的な期限情報。この期間に、普段はコスト的に躊躇する長時間ループやマルチエージェント構成を試しておくのが得策。逆に 7/19 以降は条件が戻る前提で本番ワークフローを設計すべき。

Fable 5 のコストが現実問題に — Cursor 実測「$17.32/タスク」、Grok 4.5 は「$1.51」

Cursor が公開したエージェント評価で、Fable 5 Max は正答率 70.5% で 1タスクあたり $17.32、Grok 4.5 High は 66.7% で $1.51 という実測値が示された。性能差 4ポイントに対してコストは11倍で、「4時間で $500 溶かした」という体験談とともに価格論争が噴き上がっている。

キーポイント

  • Fable 5 Max: 正答率 70.5% / $17.32 per task（Cursor のエージェント評価）
  • Grok 4.5 High: 正答率 66.7% / $1.51 per task。性能差4ptに対しコストは約11倍
  • 日に千タスク回すエージェントなら $17,000 vs $1,500 の差になる計算
  • 提唱者の Prajwal Tomar は「値付けを責めるのは筋が違う。間違った仕事を与えたのが問題」と反論
  • エージェントのコストの大半は「思考」ではなく毎ターン読み直す“コンテキスト”＝キャッシュが請求書の大半を占める、という指摘も
  • 数値は Cursor の評価環境・特定ベンチでの実測。タスク性質が変われば比率も変わる
「一番賢いモデルを常用する」設計が、エージェントを回した瞬間に破綻するという実データ。難所だけ Fable 5、定型は安いモデル、というモデル振り分けとコンテキスト圧縮が、これからのループ設計の必須スキルになる。

Supabase「State of Startups 2026」— Claude Code が必携に、Cursor は19%減、AI生成コードが主流化

Supabase がスタートアップ開発者2,000人に実施した年次調査。2025→2026 で Anthropic が採用面で一人勝ちし、Claude 有料契約は 28%→59% とほぼ倍増して OpenAI（39%）を逆転した。同時に61%のスタートアップでコードベースの過半が AI 生成となる一方、AI ヘビーユーザーの収益化率はむしろ低いという逆説的な結果も出た。

キーポイント

  • Claude 有料契約 28%→59% と倍増し OpenAI(39%) を逆転。モデル採用率は Anthropic 64% vs OpenAI 52%
  • Claude Code が必携ツール化する一方、Cursor は 19% 減
  • 61% のスタートアップでコードベースの過半が AI 生成。40% は 75% 超
  • ただし AI ヘビーユーザーの収益化率は 31% で、AI 不使用勢（56%）より低い
  • エージェント: 52% が構築中、24% がマルチエージェントを本番投入
  • だが 59% は AI ワークロードを監視しておらず、47% はプロンプト管理の仕組みを持たない＝運用インフラの空白
  • ソロ創業者が 61%（+8pt）、40歳以上の創業者が 18%→25% に増加
「AI を大量に使う＝儲かる」ではないという冷たい事実と、監視・プロンプト管理という運用インフラがごっそり空いているという事実。後者はそのまま個人開発者の勝ち筋（作るべきプロダクト）になる。

Graphify — コードベースを「クエリできる知識グラフ」に変える OSS スキル

AI コーディングで本当に難しいのは「コードを書くこと」ではなく、巨大プロジェクトの「どこが、なぜ、繋がっているか」を正しく把握することだ、という問題意識から生まれた OSS。Graphify は 1コマンドで任意のフォルダをクエリ可能な知識グラフに変換し、コード・SQL・ドキュメント・画像を横断して検索できるようにする。

キーポイント

  • 1コマンドで任意のフォルダを「クエリできる知識グラフ」に変換
  • コード・SQL・ドキュメント・画像を横断して関係性を辿れる
  • Claude Code / Cursor / Codex / OpenCode / Gemini CLI などから使えるスキルとして提供
  • 導入は `npx skills add safishamsi/graphify` の1行
  • Karpathy が示した「LLM Knowledge Bases」ワークフローの実装として、提唱の48時間後に GitHub に登場した経緯で話題化
  • 星数はコミュニティ紹介ポストの申告値で幅がある（7〜8万★級）
大規模コードベースでエージェントが迷子になる問題への直球の解。grep でファイルを漁らせるのではなく、構造を先に渡すというアプローチは、コンテキスト代を圧縮する（＝上のコスト問題に効く）実装でもある。

Kenn Ejima「自動化しない判断こそが大事」— Vibe Coding 時代の万能感への警鐘

Claude や Codex で何でも自動化できるようになった結果、「万能感」を覚えて必要以上に作り込み、自己満足に陥る人が増えている——というエンジニア Kenn Ejima 氏の指摘。自動化はプロセスを一気に硬直化させるため、むしろ「自動化しない」判断のほうが重要だと説く。

キーポイント

  • 自動化は硬直化とセット。世の中は変化し続けるので、変化する部分を固定化するとズレが広がるばかりになる
  • イーロン・マスクの5ステップ: ①本当に必要か ②スコープを小さくできないか ③単純化できないか ④運用して改善サイクルを回せているか ⑤そこまでいって初めて自動化
  • 「これを逆順でやってる人は多い。イーロン自身でさえかつてはそうだった」
  • 「自動化の技をマスターしている人ほど、自動化は最後までしない」
  • 「自動化してる感」が実際の課題解決の代わりになる自己欺瞞への警告
AI で「作れてしまう」ようになると、作る必要のないものまで作り、しかもそれを成果だと錯覚する。手で3回やってから自動化する——くらいの規律を、ループを組む前のチェックリストとして持っておきたい。

LangChain 創業者「コンテキスト窓は広がったが、無限ではない」— compaction が長期エージェントの肝

LangChain 創業者 Harrison Chase が40分のインタビューで、「コンテキスト窓は大きくなったが、それでも無限ではない。どこかで必ず compaction（圧縮）が要る」と述べた。長期horizon エージェントの設計は compaction ＋ ファイルシステム ＋ メモリ の3点セットに集約される、という整理を示している。

キーポイント

  • 「コンテキスト窓は大きくなったが無限ではない。どこかで必ず compaction が要る」
  • 「コンテキストエンジニアリングという言葉は、我々が LangChain でその名前を知らないままずっとやってきたことそのものだ」
  • 長期horizon エージェントの設計は compaction ＋ ファイルシステム ＋ メモリ の3点セット
  • 窓を広げる競争ではなく、何を捨て何をファイルに逃がすかの設計が本丸という主張
  • 引用は紹介ポスト経由。原典は40分のインタビュー動画
コンテキストがコストの主因（今日の Fable 5 コスト問題）である以上、compaction は品質の話であると同時に経済の話でもある。長く回るループを作るなら、記憶をファイルに逃がす設計を最初から入れておくべき。
