Claude Code、既定のOpusが5.5に。再開まわりも大幅修正

Claude Code 2.1.280 で Claude Opus 5.5（claude-opus-5-5）が既定の Opus モデルになりました。コンテキストは100万トークン、API単価は入力4ドル／出力20ドル（100万トークンあたり）、キャッシュ読み取りは0.20ドルです。翌日の 2.1.281 では、Claude apps gateway の Bedrock upstream に STS でのロール引き受けと Guardrail 適用が加わり、セッション再開時に履歴が変形してプロンプトキャッシュが切れる不具合がまとめて直りました。

キーポイント

  • 2.1.280: Opus 5.5 が既定に。1Mコンテキスト、入力$4／出力$20（per Mtok）、キャッシュ読み取り$0.20
  • 2.1.280: CLAUDE_CODE_MAX_MCP_DESCRIPTION_LENGTH で MCP 説明文の2,048文字上限を変更できる
  • 2.1.280: シンボリックリンク越しの書き込みが「リンク先」で判定されるよう修正。acceptEdits や auto mode が作業ツリー外への書き込みを通さなくなった
  • 2.1.281: Bedrock upstream に assume_role（別AWSアカウント可・開発者ごとのセッション可）と guardrail {id, version} を追加
  • 2.1.281: settings.json の "attribution": false でコミット／PRの帰属表示を隠せる。ただし古いCLIはこのキーを含む設定ファイルごと無視するため、混在環境ではオブジェクト形式を維持する
  • 2.1.281: 巨大セッションの再開で直近数件しか復元されない、ツール実行中に終了したセッションの再開が壊れる、といった不具合を修正
アップデート後は明示指定がなければ Opus 5.5 が使われるので、料金設定とモデル固定の有無を /model で一度確認しておくのが安全です。長時間セッションの再開に失敗していた人は、2.1.281 まで上げるだけで直る可能性があります。

Codex 0.156、フルスクリーンと/usage。0.156.1でSol／Luna

Codex CLI 0.156.0 で、次回起動から使える任意のフルスクリーンUI（/tui）、既定オンになった音声会話、利用状況を見る /usage ダッシュボードが入りました。worktree サポートも既定オンになり、エージェントのコマンドセンターからステータス絞り込みと worktree セッション作成ができます。翌日の 0.156.1 はホットフィックスで、モデルピッカーに GPT-6 Sol と GPT-6 Luna が追加され、レート制限時の切替案内では Luna が推奨されます。

キーポイント

  • /tui で次回起動から任意のフルスクリーンUI。トランスクリプト検索、マウス選択、右クリックコピーに対応
  • 音声会話が既定オン。F8でトグル、/voice settings で声を選べる。Linux／Windows向けの音声ランタイムを同梱
  • /usage でアカウント利用状況・トークン総量・プラグイン／スキルの活動を確認できる
  • worktree サポートが既定オン。コマンドセンターからステータス絞り込みと worktree セッション作成
  • /daemon でローカル背景サーバーを更新、--no-daemon で迂回できる
  • 0.156.1: モデルピッカーに GPT-6 Sol / Luna を追加。レート制限時の切替案内は Luna を推奨
音声が既定オンになったのは共有オフィスだと事故のもとです。上げる前に /voice settings でオフにする手順を決めておき、上げた後は /usage とモデルピッカーで Sol／Luna が見えるか確認するのが安全です。

GitHub CopilotにGPT-6 SolとLunaが追加

GitHub Copilot のモデル選択に、GPT-6 Astra に続いて GPT-6 Sol と GPT-6 Luna が加わりました。Sol は対話・エージェント両方向けのバランス型で、丁寧な多段検証が要る開発作業に向きます。Luna は軽量・低コスト寄りで、GPT-6 ファミリーでは最も安い選択肢です。どちらも従量課金で、ロールアウトは段階的です。

キーポイント

  • Sol は Copilot Pro+ / Max / Business / Enterprise 向け
  • Luna は Copilot Pro を含む各プラン向けで、GPT-6 ファミリー最安
  • VS Code、Visual Studio、Copilot CLI、cloud agent、Copilotアプリ、github.com、モバイル（iOS/Android）、JetBrains、Xcode、Eclipse のピッカーから選べる
  • どちらも従量課金（usage-based billing）
  • Business / Enterprise は Copilot 設定のモデルポリシーで制御。既定では新規モデルが自動で有効になる
  • ロールアウトは段階的で、まだ見えない環境もある
重い実装は Sol、短い修正や件数の多い処理は Luna、と用途で切り分けられるようになりました。Business / Enterprise は新規モデルが自動で有効になる設定なので、管理者は意図した通りか一度ポリシーを見ておくと安心です。

CopilotアプリのローカルSandboxをプロジェクト単位で設定

GitHub Copilot アプリで、ローカルSandbox がパブリックプレビューになりました。ローカルリポジトリと作業ツリーのセッションに対して、ファイル・ネットワーク・認証情報へのアクセス範囲をプロジェクト単位で設定できます。プロジェクト設定はアプリが要求するポリシーで、エンタープライズ管理設定があればさらに厳しい側が効きます。

キーポイント

  • 設定できるのは3種類。Filesystem（追加の読み書き／読み取り専用／拒否フォルダ）、Network（外向き通信とローカルネットワーク）、Credentials（HTTPS git 用の認証情報と GitHub CLI の認証情報）
  • 既定はオフ。アプリ設定でプロジェクトを選び「Sandbox new sessions」をオンにする
  • 反映されるのは新規セッションから。実行中のセッションは /sandbox on でその場だけ有効化できる（プロジェクト既定は変わらない）
  • OSが要求ポリシーを強制できない場合、サンドボックスなしで動かさずエラーで止まる
  • クラウドSandboxセッションやリモートホスト上のセッションには適用されない
  • Copilotアプリと Copilot CLI のSandbox設定は別々に管理する
エージェントが手元のファイルや認証情報に触れる範囲を、プロジェクトごとに決められるようになりました。顧客リポジトリを扱うときだけ厳しくする、といった使い分けができます。

Cloudflare Workers BuildsがCursor Originに対応

Cloudflare の Workers Builds が、Cursor Origin にホストされたリポジトリに対応しました。本番ブランチへの push で Worker を自動ビルド・デプロイし、非本番ブランチのビルドを有効にすると各ブランチにプレビューURLが発行されます。ビルド状態とプレビューリンクは Cursor Origin のPRへ投稿され、トリガーされたビルドごとにチェックランが作られます。

キーポイント

  • 本番ブランチへの push で自動ビルド・デプロイ
  • 非本番ブランチのビルドを有効にすると、バージョン固有のプレビューURLと、最新ビルドを追う安定プレビューURLの2本が出る
  • Cursor Origin のPRにビルド状態とプレビューリンクを投稿
  • トリガーされたビルドごとにチェックランを作成
  • 設定手順は Cursor に Cloudflare アプリを入れ、アクセスを許すリポジトリを選ぶところから
リポジトリの正本を Cursor Origin に置いていても、GitHub と同じ流れで Workers の本番とプレビューを回せます。GitHub へミラーを作らずに、PR上でビルド結果を追えるのが利点です。

Vercel Blobのストア数が全プランで無制限に

Vercel Blob のストア作成上限（Hobby 100／Pro 500／Enterprise 1,000）が撤廃され、必要なだけ作れるようになりました。ストア作成は put() / copy() / list() と同じ Blob Advanced Operations として課金され、Pro は100万回あたり5ドル、Hobby は月2,000回の無料枠に含まれます。ストアの削除は無料です。

キーポイント

  • 旧上限（Hobby 100／Pro 500／Enterprise 1,000）を撤廃
  • ストア作成は Advanced Operations 扱い。Pro は100万回あたり5.00ドル、Hobby は月2,000回の無料枠内
  • 削除は無料
  • 本番・ステージング・プレビューでストアを分け、環境ごとに別の認証情報を渡せる
  • マルチテナントでは顧客ごとにストアを切り、1回の呼び出しでそのテナントだけエクスポート／削除できる
  • 同じデータを複数ストアに分けても、ストレージ・操作・転送の課金は変わらない
  • ストア作成は使用量ページと Observability ダッシュボードの Blob Advanced Operations に表示される
パス名の命名規則で環境やテナントを分けていた運用を、ストアという固い境界に置き換えられます。プレビューブランチや移行用に作って終わったら消す、という使い方も削除が無料なのでやりやすくなりました。

〈知見〉Claude CodeからJevを使う3つの経路

過労くん（@karoukun_ai）が、Claude Code から Jev を使う経路を公式スキル・MCPサーバー・モデル選択用プロキシの3つに整理した記事です。あわせて、文脈の選別や出力の検証を担う有志の実装もまとめています。筆者自身が検証したのは招待の取得と公式スキルの導入までで、紹介したツールすべての動作確認ではないと明記されています。

キーポイント

  • Claude Code から Jev を使う経路を、公式スキル／MCPサーバー／モデル選択用プロキシの3系統に分けて整理
  • 文脈の選別（どの情報を渡すか）と出力の検証を担う有志実装も併記
  • 筆者の実体験は招待取得と公式スキル導入の範囲。関連ツール全部の検証報告ではないと断っている
  • 確率の高い回答でも誤りうる点と、モデルを切り替えるとプロンプトキャッシュに影響が出る点を注意として挙げている
新しいモデルを既存のエージェントに繋ぐとき、選択肢は「公式スキル／MCP／プロキシ」のどれかに落ち着きます。この3分類は Jev に限らず使える地図なので、自分の構成がどれに当たるかを先に決めると迷いが減ります。

〈知見〉UIの動きを「種類・イージング・速さ」から逆引きする

UIモーションの実例を「動きの種類・イージング・速さ」から逆引きできる辞典サイト MOTION MOVEMENT REFERENCE が紹介されています。完成物をギャラリーで眺める形ではなく、動きの属性で絞り込んで探せるのが特徴です。投稿は3,859ブックマークを集めており、その場で見るより作業中に引きに来る使われ方がうかがえます。

キーポイント

  • 動きの種類・イージング・速さという属性でモーションの実例を検索できる
  • ギャラリー型と違い、再現に必要なパラメータ（どのイージングを何ミリ秒で）に辿り着ける
  • AIに動きを指示するときの語彙として使える。「かっこよく」ではなく「ease-out で 250ms のスライドイン」と書けると出力が安定する
  • 3,859ブックマーク／179,415ビュー。保存率の高さが参照用途であることを示している
LPやアプリの「なんか気持ち悪い動き」を直すとき、言葉にできないと議論が収束しません。動きを属性で言語化できる辞書を1つ持っておくと、実装者にもAIにも同じ絵を渡せます。
